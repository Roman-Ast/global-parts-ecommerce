# Global Parts — Контекст проекта для агента

Этот файл — справочник архитектурного и бизнес-контекста для in-editor агента.
Обновляйте его по мере крупных изменений в пайплайне.

## О проекте

Global Parts (shop.globalparts.kz) — интернет-магазин автозапчастей в Астане, Казахстан.
Модель: asset-light dropshipping от ~10 поставщиков (Rossko, Shatem, Interkom, ForumAvto,
TISS и др.) с доставкой день-в-день/на следующий день как ключевым конкурентным
преимуществом. Единственный разработчик и оператор — Roman.

Каналы продаж: Kaspi Marketplace (основной), собственный сайт, 2GIS, OLX, повторные/
реферальные заказы. Стек: Laravel/PHP/MySQL.

## Архитектура Kaspi-пайплайна

Основной поток команд:
```
prices:fetch → offers:aggregate → kaspi:match → kaspi:reprice →
kaspi:sync-feed → kaspi:feed-cleanup → kaspi:generate-xml
```
Еженедельно (поиск новых карточек): `kaspi:parse-sku` → `kaspi:bind-products`

### Ключевые таблицы
- `kaspi_initial_products` — неизменяемый источник истины, репрайсинг никогда его не трогает
- `supplier_offers` — слой агрегации, `UNIQUE KEY (sku, supplier_name, brand)`
- `kaspi_competitors` — конкурентные офферы по позициям
- `parts_catalog` — используется для подготовки Ozon-фида (скрейпинг публичных карточек Kaspi)
- `kaspi_feed_items` — колонка `bound` отмечает привязанные к мастер-карточкам товары

### Важные классы/команды
- `MatchKaspiSkuCommand.php` — матчинг по артикулу; здесь же константа `DISABLED_SUPPLIERS`
  для временного отключения поставщика без потери данных (сейчас используется для ForumAvto)
- `AggregateSupplierOffersCommand` — партиционирует офферы по `(sku, brand)`, не просто `sku`;
  здесь же `EXCLUDED_SKUS`, `BRAND_ALIASES` (напр. `lemfoerder`/`lmi` → `lemforder`),
  `QTY_OVERRIDE_KEYWORDS`, `QTY_OVERRIDE_ARTICLES`, `FIXED_COST_KEYWORDS`
- `RepriceKaspiCommand` — динамический репрайсинг; anomaly detection блокирует только
  понижение цены при `$flag === 'risk'`, повышения не блокирует
- `KaspiPriceCalculator` — `COMMISSION=0.125`, `TAX=0.04`, `FEES_DIVISOR=0.835`;
  прогрессивная маржинальная шкала (50к-120к сегмент — 35%, 120к+ — 34%),
  `MIN_ABS_MARGIN` — абсолютный пол в тенге, `min_margin_dumping` сегмент — намеренно
  ~15% каталога с минимальной маржой для конкурентного покрытия
- `GenerateKaspiXml` — здесь `EXCLUDED_NAME_PATTERNS`; XML namespace `xmlns="kaspiShopping"`,
  порядок элементов строго `model → brand → availabilities → price`
- `KaspiFeedCleanupCommand` / `deactivateStaleFeedItems()` — деактивация устаревших/
  осиротевших офферов
- `SlugHelper::brandToSlug()` — полная транслитерация кириллических брендов, обязателен
  `?string` type hint (NULL brand ломал слаги и давал 5xx)

### Иконка возврата в выдаче (добавлено 2026-08-24)
Каждая строка результата (`partials/items/*.blade.php`, все 4 секции) несёт
колонку с иконкой `fa-triangle-exclamation`: жёлтая (`text-warning`) с
подсказкой "международный возврат невозможен" для Avtozakup/Radle/Phaeton
Local (последний добавлен 2026-08-25 по просьбе Романа), зелёная
(`text-success`) с выжимкой из ЗПП (14 дней, товарный вид, чек) для всех
остальных. Управляется ключом `'returnable'` в массиве строки — по
умолчанию `true` (`?? true` в партиалах), у этих трёх явно `false`.
**Если добавляется ещё один поставщик без возможности возврата —
проставить `'returnable' => false` в его методе, ничего в партиалах менять
не нужно.** На мобилке иконка — абсолютным позиционированием в правом
верхнем углу карточки, РЯДОМ с info-иконкой (`right: 34px`, не `left:
10px` — там уже сидит бейдж бренда, порядок 1 в потоке, из-за чего иконки
раньше садились друг на друга). Тултипы — через
Bootstrap `data-bs-toggle="tooltip"`, инициализация `new
bootstrap.Tooltip()` вручную на каждый новый узел в `insertRows()`
(`partSearchRes.blade.php`) — сам атрибут без явной инициализации не
работает, а строки грузятся пачками уже после первого рендера.

### Матчинг: важный баг и фикс
Короткие артикулы (напр. `BW0010`) матчились по substring на карточки для `BW0010-07-2`,
что вызывало продажи ниже себестоимости. Исправлено: `normalizeArticle()` + word-boundary
regex вместо `str_contains()`, плюс fallback-цикл, постепенно упрощающий поисковый запрос
Kaspi при сохранении строгой фильтрации по артикулу.

## Поставщики — особенности парсеров

- **Kulan** (`kulanoil.kz`) — только колонка "Нур-Султан", `preorder_days=0`
- **ZakazAutoKostanay** — имя файла содержит `zakazauto` + `kostanay`/`kst`, `preorder_days=7`
- **Tstarter** — файл `Astana_ostatki_Tstarter`, 6 колонок, цены в KZT несмотря на
  заголовок "руб"
- **Interkom** — multi-sheet xlsx (`MultiSheetParserInterface`), `.xls` ~18MB падает
  тихо — вероятно memory/timeout при `SimpleXLS::parse()`
- **ForumAvto** — два парсера LP/GP; GP-поставщик удалён из БД полностью, LP реактивирован;
  сейчас LP временно отключён через `DISABLED_SUPPLIERS`
- **Phaeton/Shatem** — детекция приоритизирует `bodyLower` (тело письма) над `From`
  заголовком, т.к. письма часто пересылаются вручную
- **TISS** — с 2026-08-23 на API v2 (см. открытые задачи, п.2) — старая проблема
  пустого `offers` относилась только к v1
- **Rossko** — `searchRossko()` классифицирует склад по подстроке в `description`
  ("Астана" → в наличии, "Павлодар"/"Караганда" → под заказ), другие значения
  (напр. "Партнерский склад") молча отбрасываются, результат для них никуда не
  попадает — НЕ баг, оставлять как есть (Роман подтвердил 2026-08-24): Rossko
  подключён к тем же складам, что уже есть напрямую (Фебест, Фаэтон, Армтек и
  т.д.), так что это в основном дубли, терять их не жалко

3. **504 на обычном поиске сайта — в процессе решения через прогрессивную
   подгрузку (начато 2026-08-15, не докручено, продолжать отсюда).**

   Исходная причина (лог `production.ERROR`, обнаружено 2026-08-15):
   `SparePartController::getSearchedPartAndCrosses()` (вызывается из
   `catalogSearch()` / роут `POST /getPart`) опрашивает 18+ поставщиков
   **строго последовательно** — `searchArmtek`, `searchGerat`,
   `searchShatem`, `searchPhaeton`, `searchTreid`, `searchTiss`,
   `searchKulan`, `searchFebest`, `searchForumAuto`, `searchIngvar`,
   `searchVoltage`, `searchBlueStar`, `searchInterkom`, `searchAdilPhaeton`,
   плюс условно `searchAutopiter`/`searchAvtozakup`/`searchRossko`. У
   каждого свой таймаут (2-8 сек через `curl`/`SoapClient`/`Http`,
   константы `CONNECTION_TIMEOUT=2`/`TIMEOUT=3`), но т.к. вызовы идут один
   за другим — суммарное время легко перескакивает 30-60 сек и обрывается
   по gateway timeout. Попутно найден и исправлен отдельный баг в той же
   функции (не причина 504): TypeError на `logSearchIfNotAdmin()` при
   отсутствии `partNumber` в запросе (лишний второй аргумент при
   однопараметрической сигнатуре + нестрогая типизация).

   Выбранное решение — не распараллеливание, а **прогрессивная загрузка**:
   рендерить страницу результатов мгновенно (без единого обращения к
   поставщику), а сами данные подгружать отдельными запросами по мере
   готовности, пока пользователь уже видит страницу. Решили так вместо
   параллелизации (`curl_multi` для простых REST — уже был готовый
   прототип, но эксперимент показал: параллельные запросы к Shatem ломали
   друг друга через гонку за токеном авторизации на холодном кеше — раньше
   `getShatemToken()` не использовался в `searchShatem()` вовсе, каждый
   вызов логинился заново; теперь `Cache::lock()` вокруг
   `cache()->remember('shatem_token', ...)` решает и это, но полная
   параллелизация всё равно осталась бы хрупкой для многошаговых
   поставщиков типа Shatem/Treid).

### Статус "Рабочие" — замена хардкода EXCLUDED_PHONES/EXCLUDED_GROUP_NAMES (2026-09-19, поведение исправлено 2026-09-21)

Раньше личные номера Романа/коллег и рабочая группа "Темщики" жёстко
исключались в `WhatsAppWebhookController` константами `EXCLUDED_PHONES`/
`EXCLUDED_GROUP_NAMES` ДО появления лида — их переписка вообще не
попадала в `whatsapp_leads`/`whatsapp_messages`. По решению Романа
2026-09-19 хардкод убран целиком: такие контакты теперь заводятся лидами
как обычно (видны в "Новые"), а дальше Роман сам вручную переносит их в
статус `LeadStatuses::STAFF_STATUS` ("Рабочие", вторая колонка на доске,
сразу после "Новые" — единственная не-воронка-продаж колонка, которая при
этом РЕАЛЬНАЯ, с видимыми карточками, в отличие от "Спам" — у того своей
колонки нет, только счётчик-корзина).

**Первая версия (2026-09-19) была самопротиворечивой** — Роман сам
поймал это на следующий день: `WhatsAppWebhookController` при переносе в
"Рабочие" переставал СОХРАНЯТЬ сообщения вообще (тот же ранний `return`,
что раньше был у исключённых номеров) — но тогда и смотреть в колонке
"Рабочие" было НЕЧЕГО, она осталась бы пустой навсегда после переноса.
**Исправлено 2026-09-21**: сообщения от "Рабочие"-лидов пишутся в
`whatsapp_messages` СТРОГО КАК ОБЫЧНО (webhook больше вообще не проверяет
`status` лида) — вместо этого исключение перенесено на этап АНАЛИЗА, в
три места разом:
- `WhatsappMessageObserver::created()` — сразу после проверки фичи-флага
  `WHATSAPP_LLM_EXTRACTION_ENABLED` проверяет `status` лида и выходит
  раньше, чем дойдёт до платного вызова Claude — "Рабочие" никогда не
  тратят деньги на LLM-разбор и никогда не создают `lead_requests`.
- `whatsapp:test-analysis` — дефолтная выборка "самые активные диалоги"
  исключает `status=staff` (явный `--lead=<id>` всё ещё может указать на
  такой лид намеренно, для отладки самого механизма).
- `whatsapp:analyze-demand` — доп. страховка `whereHas('lead', status !=
  staff)` поверх основного фильтра, на случай если `lead_requests`
  всё-таки появится для такого лида каким-то другим путём.

История, сохранённая ДО и ПОСЛЕ переноса в "Рабочие", не удаляется и не
трогается — просто никогда не участвует в LLM/ручном анализе спроса.

### Восстановление сообщений после простоя локального сервера — `whatsapp:recover-history`

Вебхук шлётся на локальный dev-сервер Романа — если тот выключен (2026-09-16,
компьютер выключали ради установки PCI-E модема), входящие сообщения не
теряются на стороне Green API (они остаются в истории чата), но и не
попадают в нашу БД сами. Штатный способ вычитать пропущенное —
`receiveNotification`/`deleteNotification` (реализовано в
`DrainGreenApiQueueCommand`, `whatsapp:drain-queue`) — **на практике не
работает**: живьём подтверждён документированный баг Green API (GitHub
green-api/issues #1115 и #1118) — счётчик очереди в консоли Green API
показывает ненулевое значение, но `receiveNotification` стабильно отдаёт
пустой ответ, даже на выделенном под инстанс поддомене
(`https://7107.api.greenapi.com`, не только на общем `api.green-api.com`).

**Рабочий обходной путь** — `whatsapp:recover-history {--since=} {--source=}
{--history-count=50} {--dry-run}`: `getChatHistory` читает историю
напрямую из WhatsApp, не из очереди уведомлений, и этот путь баг не
затрагивает. Идёт по списку чатов (`getChats`, отсортирован по свежести
последнего сообщения) сверху вниз, тянет `getChatHistory` на каждый,
останавливается на первом чате, где самое свежее сообщение уже старше
`--since` (дальше в списке будет только ещё старее — весь остаток чатов
безопасно пропустить). Каждое новое сообщение (дедуп по `idMessage` в
`whatsapp_messages`) реконструируется в вебхук-подобное тело и
прогоняется через тот же `WhatsAppWebhookController::handle()`, что и
живой вебхук — та же логика исключений/парсинга типов сообщений/upsert
лида, ничего не задублировано.

**Важно — `getChatHistory` систематически ловит HTTP 429** при
последовательном обходе многих чатов подряд (живьём — примерно через
чат на второй), без ретрая такой чат молча выпадает из восстановления
целиком. Команда ретраит 429 три раза с нарастающей паузой (2/5/10 сек)
+ `usleep(400ms)` между чатами — на живом тесте (2026-09-17, оба
инстанса, 47 чатов суммарно) это свело 429 к нулю.

**Живой прогон 2026-09-17** (окно `--since="2026-09-16 16:30"`,
покрывает простой ~2026-09-16 17:05 → 2026-09-17 15:25): восстановлено
253 сообщения (2gis) + 150 (site) = **380 сообщений, 41 лид** —
последнее сообщение в БД после прогона совпало с реальным текущим
временем, разрыв закрыт. Если понадобится повторить на будущий простой
— команда параметризована (`--since`), ничего менять в коде не нужно,
дедуп по `idMessage` не даст задвоить уже сохранённое.

### Масштабирование доски/мессенджера — лимит по свежести, не по дате (2026-09-17)

Роман поднял вопрос заранее (базе ещё далеко до размера, где это стало
бы заметно тормозить, но правильно решить архитектурно сразу): и
`KanbanBoard::render()`, и `WhatsappMessenger::render()` тянули **всех**
лидов без лимита на каждый `wire:poll.3s` — с ростом `whatsapp_leads`
это стало бы расти линейно и не остановилось бы само.

**Отклонённый вариант — фильтр по календарной дате** ("показывать только
за последний месяц"): ломается на сценарии "лид молчал 2 месяца, написал
сегодня" — с фиксированным окном такой лид не попал бы в выборку, хотя
это ровно тот случай, где ответить важнее всего.

**Выбранное решение — лимит по свежести, не по дате**: `ORDER BY
last_seen_at DESC LIMIT 200` (`KanbanBoard::LEADS_LIMIT` /
`WhatsappMessenger::LEADS_LIMIT`, сейчас 200 в обоих). Лид, который
написал сегодня, **любой** давности молчания — сразу поднимается наверх
списка (`last_seen_at` обновляется на `now()` при каждом новом
сообщении, `WhatsAppWebhookController::handle()`) и автоматически
попадает в лимит вне зависимости от календарной даты. Старые
невостребованные лиды просто вытесняются из рабочей выборки по мере
роста базы — из БД не удаляются, вьюха канбана/мессенджера просто не
единственный доступ к данным.

**Заодно найден и исправлен реальный источник нагрузки, более острый, чем
сам лимит**: `WhatsappMessenger::render()` грузил `with(['messages' =>
latest()])` — **всю историю сообщений всех лидов разом** на каждый
рендер, хотя список слева использует только `messages->first()` ради
превью (остальное впустую). Исправлено — список теперь берёт `lastMessage`
(`latestOfMany()`, та же связь, что уже была в `WhatsappLead` под
`KanbanBoard`), а полная история грузится ТОЛЬКО для реально открытого
чата (`activeLeadId`) и только последние `ACTIVE_CHAT_MESSAGES_LIMIT=60`
сообщений (`WhatsappMessage::where(...)->latest()->limit(60)->get()
->reverse()`, порядок для блейда — от старых к новым, он скроллит к
последнему). Подгрузка более старых сообщений при скролле вверх — не
реализована (не просили, отдельная задача на будущее, если понадобится
глубже 60 последних сообщений в одном чате).

### Локалка на PHP 8.3, прод — на 8.2.33: `composer.json` теперь пинит платформу (2026-09-17)

При первом деплое CRM на прод `composer install --no-dev` упал:
lock-файл держал `maennchen/zipstream-php 3.2.2`, которому нужен PHP
^8.3, хотя сам `composer.json` объявляет `"php": "^8.2"`. Причина —
локальная машина агента на PHP 8.3.31, прод — на 8.2.33
(`/opt/plesk/php/8.2`); когда добавлялся `anthropic-ai/sdk` (коммит
`7bb70e5`), composer резолвил lock-файл на локальной 8.3 и без единого
предупреждения затянул версию транзитивной зависимости, несовместимую с
тем PHP, что реально стоит на проде — `^8.2` в `require` этого не ловит,
это ограничение только на СВОЙ пакет, не на резолюцию транзитивных.

**Исправлено**: `composer.json` → `config.platform.php = "8.2.33"` —
теперь composer на ЛЮБОЙ машине (включая локальную 8.3) резолвит
зависимости так, как будто запущен на прод-версии PHP, и такой рассинхрон
больше не проскочит молча. `zipstream-php` даунгрейжен на `3.1.2`
(без `--with-all-dependencies` — тот флаг задел почти весь граф,
включая `symfony/console` 7.2→7.4, что сразу сломало `artisan
package:discover` с невнятным `Call to a member function make() on
null`; откатил и сделал точечный `composer update maennchen/zipstream-php`
без флага — резолвится в рамках уже существующих ограничений
`phpoffice/phpspreadsheet` (`^2.1||^3.0`), трогает только один пакет).

**Если на проде снова всплывёт что-то похожее** ("your lock file does
not contain a compatible set of packages... requires php-64bit ^8.X") —
это тот же класс проблемы: локальная резолюция на другой версии PHP,
чем прод. Первым делом проверить `php -v` на обеих машинах, при
расхождении — обновить `platform.php` в `composer.json` под актуальную
версию прода и точечно (БЕЗ `--with-all-dependencies`) обновить только
проблемный пакет.

### `proc_open` навсегда выключен на проде (шаринг, подтверждено Романом 2026-09-17) — composer install ТОЛЬКО с `--no-scripts`

Прод — шаред-хостинг (Plesk), `proc_open` отключён на уровне PHP
глобально и без возможности включить ("шаред, всё закрыто" — Роман).
Обычный `composer install`/`composer update` на этом хосте **всегда**
будет падать на пост-хуках (`post-autoload-dump`/`post-update-cmd` —
`package:discover`/`vendor:publish`), потому что сам composer запускает
`@php artisan ...` КАК ПОДПРОЦЕСС через `proc_open` — это ограничение
самого composer'а, не Laravel (проверено живьём: `php artisan
package:discover` напрямую через шелл с искусственно отключённым
`proc_open` отрабатывает нормально, падает только способ его запуска
изнутри composer).

**Правильная последовательность на проде — всегда так, не разово**:
```bash
composer install --no-dev --optimize-autoloader --no-scripts
php artisan package:discover --ansi
php artisan vendor:publish --tag=laravel-assets --ansi --force
php artisan config:clear
```
Без `--no-scripts` первая команда упадёт с `Process class relies on
proc_open, which is not available` сразу после успешной установки
пакетов (сами пакеты при этом уже скачаны и распакованы корректно —
падает именно пост-хук, не сама установка).

### 503 на сайте после деплоя через Plesk Git — причина и фикс (подтверждено Романом 2026-09-19)

Plesk-деплой ("Развернуть сейчас") перед подтягиванием обновлений с git
сам переводит приложение в service/maintenance-режим (аналог `php artisan
down`). Если в этот момент связь до GitHub обрывается/зависает (та же
сетевая нестабильность, что несколько раз в этой сессии рвала `git push`
у агента) — git-запрос внутри Plesk не отвечает, и приложение так и
остаётся в maintenance-режиме, даже когда сеть отпустит: снаружи это
выглядит как 503 на всём сайте, хотя реальная причина не крэш и не
PHP-FPM, а просто забытый maintenance-флаг.

**Фикс** — `php artisan up` через PHP-командную строку в Plesk (тот же
инструмент, где обычно гоняешь `migrate --force`). Подтверждено живьём
2026-09-19 — сразу решило проблему. Быстрее и надёжнее, чем то, что
пробовали раньше (пересохранение PHP Settings ради рестарта FastCGI-пула,
~5 минут ожидания) — тот способ иногда совпадал по времени с
самостоятельным восстановлением сети, а не решал причину напрямую.

### "Пора напомнить" — напоминание менеджеру о зависших лидах (2026-09-21)

Дизайн согласован с Романом заранее (явно попросил сначала договориться,
потом писать код). Источник правды — `LeadStatuses::REMINDER_ELIGIBLE_STATUSES`
(`offer` + все 4 подпричины `thinking`/"Работа с возражениями" —
`silent`/`expensive`/`wait`/`pending` — + `payment` ("Оплата"), т.е. везде,
где лид реально "ждёт" решения/действия клиента после НАШЕГО последнего
сообщения; `payment` подтверждён Романом отдельным сообщением тем же
днём, изначально не был включён до его прямого подтверждения).

`LeadStatuses::needsReminder(WhatsappLead $lead): bool` — true, если статус
лида eligible И последнее сообщение (`lastMessage`, `latestOfMany`) НАШЕ
(не входящее) И прошло `REMINDER_THRESHOLD_HOURS=3` часа с его отправки.
Требует, чтобы `lastMessage` была заранее подгружена (не делает свой
запрос) — вызывается в `KanbanBoard::render()` на уже загруженной пачке
лидов, где эта связь и так нужна для превью последнего сообщения.

**Подсветка — не лесенка интервалов.** Обсуждали 3ч/1д/3д — Роман явно
отклонил как усложнение без практической разницы: подсветка загорается
один раз через 3 часа тишины и горит непрерывно, пока менеджер либо не
напишет снова (это само обнуляет таймер — последнее сообщение опять
становится "нашим, но свежим"), либо не сменит статус лида. Визуально —
жёлтая подсветка карточки (`.kanban-card-reminder`, `!important` — тот же
приём, что и у `.kanban-card-pulse` ранее в этом файле, Tailwind-via-CDN
не гарантирует порядок специфичности) + иконка часов, и счётчик того же
цвета в шапке каждой колонки/под-полосы, где есть хоть одна такая
карточка.

**Виртуальная колонка "Пора напомнить"** — второй колонкой на доске,
сразу после "Новые" (порядок — решение агента, Роману не показывался
отдельно, может попросить перенести). НЕ отдельный статус в БД — просто
карточки из уже загруженного `$leads` с `needs_reminder=true`, собранные
поперёк реальных статусов в отдельный список (`KanbanBoard::render()` →
`$remindersDue`), те же объекты моделей, не дублирование данных. Из
дизайн-обсуждения с Романом: карточку можно перетащить ОТСЮДА в реальную
колонку (это по-настоящему меняет `status` лида, как обычно) — но
затащить руками СЮДА нельзя, это не место назначения. Реализовано через
SortableJS `group: {name, pull: true, put: false}` на контейнерах с
`data-no-drop="true"` (`data-status="__reminders_readonly__"`, особый
ключ, не как у настоящих статусов).

Живая проверка — только backend-логика (6 сценариев через tinker с
`forceFill()` на `created_at`, т.к. mass-assignment тихо роняет
не-fillable поле) и blade-компиляция; полный Livewire-рендер через тест-
харнесс не удался (`Livewire::test()` падает в этом окружении на
PHPUnit-конфиге, ручной вызов `render()` дважды не работает — известное
ограничение тестирования Livewire вне реального request-цикла, не
специфично для этой фичи). Живая проверка глазами Романа на реальной
доске — следующий шаг.

## ERP (в разработке, ~95%)

Модуль расчётов: кредиторка/дебиторка, cash flow, взаиморасчёты. Есть баг в дашборде
на сценарии возврата — план перед go-live: сначала выписать на бумаге все сценарии

### Реальные продажи — только на проде, не в локальной БД (важно, 2026-09-15)

`orders`/`order_product` — правильные, боевые таблицы (те же имена что на
проде), НО локально в них всего 17/23 строки, это тестовые данные ERP
(см. truncate-между-прогонами выше), не реальная история продаж. Если
нужна настоящая история (например, посчитать топ реально продаваемых
позиций для приоритизации Ozon-каталога) — данные брать ТОЛЬКО через
Романа с прода (SQL-запрос он гоняет сам через phpMyAdmin/аналог, доступа
у агента на прод нет). `orders.sale_channel='kaspi'` — фильтр по каналу
Kaspi (проверено на локальных данных, значения также встречались:
`site`/`2gis`/`repeat_request`/`friends`). `orders.date` — `varchar`,
формат `"YYYY-MM-DD HH:MM:SS"` (сравнение строкой работает для диапазона
дат). `order_product.status` пример из локальных данных:
`payment_waiting`/`issued` — на проде статусов наверняка больше, нужно
смотреть по факту выгрузки, что считать состоявшейся продажей, а что
отменой/возвратом.

### Автоплатёж предоплатным поставщикам — убран целиком (2026-09-19)

`manuallyMakeOrder()` раньше автоматически (a) списывал зачёт (`supplier_credits`)
у поставщика, если он был, и (b) для `payment_policy='prepaid'` (Автотрейд и т.п.)
автоматически проводил недостающий остаток как платёж со счёта "Рома Kaspi Gold" —
`applyAvailableSupplierCredit()` + блок "Автооплата предоплатному поставщику" в
цикле по товарам заказа. За несколько дней это дважды давало живые расхождения
"Долг" vs "Сальдо" (2900₸ у Автотрейда 2026-09-18, затем зачёт "не двигался" после
ручной доплаты 19350 2026-09-19, т.к. обычная форма "Оплата поставщику" не умела
пополнять `supplier_credits` — был короткий фикс этого конкретного пробела, тоже
2026-09-19, но прожил меньше часа) — по прямому решению Романа автоматика убрана
целиком, а не залатана ещё раз: `applyAvailableSupplierCredit()` удалён, оба
условных блока в цикле по товарам убраны. Теперь ЛЮБОЙ поставщик (включая бывших
"prepaid") просто копит долг в `supplier_settlement`, как Rossko/Shatem/остальные,
а оплату Роман заводит вручную через `supplierPayment()` ("Оплата поставщику"),
когда сам решит — без автоматики и без различий по `payment_policy`.
`supplier_credits` как таблица не удалена (её продолжают писать
`CustomerReturnController` и разовая форма "Начальные остатки") — просто больше
ничего не пишет её на пути создания заказа/оплаты поставщику. Уже накопленные
остатки (Тисс, Кулан и т.п.) никуда не делись, но и не расходуются
автоматически — Роман учитывает их сам при оплате.

**Дашборд-виджеты "Сальдо у поставщиков (зачёт)" и "Переплата
поставщикам" — объединены в одну карточку (2026-09-19, три захода за
один день).** Сначала "Сальдо" (читала `supplier_credits`, которая
перестала обновляться на обычном пути после удаления автоплатежа)
убрали целиком как якобы дубль "Переплаты" (живой `accrued-paid` из
`getSuppliersSettlements()`) — но Роман поймал живой регресс: у Армтека
19820 существовало ТОЛЬКО в `supplier_credits` (зачёт по возврату от
поставщика, `CustomerReturnController`, `mode=credit`), в accrued-paid
такого источника вообще нет, карточку вернули. Тут же выяснилось, что
раз Роман теперь вносит оплаты поставщикам вручную без автоматики,
разница между источниками для него не имеет смысла — по его прямой
просьбе карточки объединены в одну.

`getSuppliersSettlements()` строит единый список по `supplier_id`:
переплата из accrued-paid + остаток `supplier_credits` для того же
поставщика, суммируются без задвоения. Безопасно складывать НАПРЯМУЮ
только потому, что отдельная миграция
(`2026_09_19_000005_zero_legacy_supplier_credits_for_automated_suppliers`)
предварительно обнулила `supplier_credits` у ТРЁХ поставщиков —
Автотрейд/Тисс/Кулан — у которых эта таблица исторически писалась
СИНХРОННО с убранной автоплатёжной автоматикой (их текущий остаток там
был просто зеркалом того, что и так уже отражено в accrued-paid). У
всех остальных (Армтек и подобные, зачёты по возвратам/опенинг-балансу)
такого зеркалирования никогда не было — не трогали.
`getSupplierCreditsData()` и вторая карточка удалены; формула "Чистая
финансовая позиция" упрощена обратно до одного слагаемого
(`totalSupplierOverpayment` теперь несёт всю картину).

### Автозакуп (supplier_id=34) — та же простая кредиторка, что у остальных поставщиков

У Автозакупа на их собственном сайте (avto-zakup.ru/shop/balance.html) есть предоплаченный
баланс, "в работе" (сумма не закрытых заказов) и производный от них "долг по заказам" —
живой сверкой 2026-09-02 подтверждено, что отгрузка/доставка НЕ меняет долг (баланс и
"в работе" на сайте уменьшаются синхронно на одну и ту же сумму — wash), долг растёт
только от новых заказов и падает только от реальных пополнений баланса. По прямому
решению Романа это не выделяется в отдельную модель зачёта/депозита — Автозакуп ведётся
в нашей системе как обычная кредиторка (`supplier_settlement`, `operation=realization`),
один в один как Росско/Шатэм: разовая историческая строка на старый бэклог (заказы,
размещённые до/вне ERP) + обычные новые заказы по мере поступления, оплата — обычной
формой "Оплата поставщику", когда Роман реально пополняет их баланс. На 2026-09-02
исторический остаток зафиксирован как 205336 (кредиторка на конец дня — 288799 с учётом
3 заказов дня на 83463).

(4.5–13.5% от суммы заказа) при трансграничной доставке в РФ. Экономику по марже нужно
понимать через ERP до полноценного запуска.

### `ozon:create-card` — овернайт-заливка каталога, открытый вопрос по ТН ВЭД (2026-09-11)

`ozon:create-card` (по образцу `halyk:create-card`, см. докблок в файле команды) написан
и гоняется овернайт-скриптом (`night_ozon.sh`, `--limit=5000` в цикле до исчерпания пула)
без фильтра по категории — в отличие от Halyk, здесь категоризация Ozon плоская (~464
"типов" в дереве "Автотовары"), матчинг по `characteristics.category_path` через
`findTypeInTree()` работает достаточно широко, чтобы не ограничиваться одной категорией.

**Найдено при живом мониторинге прогона на 09-11**: из ~3700 обработанных карточек только
~1280 (35%) реально ушли на модерацию, у ~1870 (50%) `resolveHsCode()` не смог подобрать
обязательный атрибут «ТН ВЭД коды ЕАЭС» и карточка целиком пропущена (ещё ~585 — обычные
cURL-таймауты на `api-seller.ozon.ru`, не системная проблема). Причина — метод ищет код по
ПЕРВОМУ СЛОВУ типа товара (сработало живьём только на "амортизатор"/"амортизаторы", см.
докблок метода), но `/v1/description-category/attribute/values/search` для ТН ВЭД — это
полнотекстовый поиск по ВСЕЙ таможенной номенклатуре ЕАЭС (не ограничен категорией товара
на Ozon — подтверждено живым запросом: `"части"` вернуло в том числе позиции про баранину),
а формулировки кодов — официальная таможенная терминология ("системы подвески и их части"),
не бытовые названия деталей ("ступица"/"сайлентблок"/"рычаг"/"датчик" — 0 результатов).
Числовой поиск по товарной позиции `"8708"` (глава ТН ВЭД "Части и принадлежности моторных
транспортных средств") стабильно возвращает релевантные подсубпозиции, включая generic-катки
"прочие: прочие: прочие" под каждым разделом (коробки передач, мосты, кузов, подвеска и
т.д.) — то есть технически есть из чего построить фолбэк, но выбор конкретного "прочие"-кода
для товара, для которого мы НЕ знаем точную деталь — это уже таможенная классификация, а не
чисто техническая эвристика (риск неверного кода при трансграничной FBS-доставке в РФ, см.
абзац о штрафах выше) — **осознанно не стал реализовывать автоматический фолбэк без
подтверждения Романа**, оставил как есть.

**Важно — почему это не просто "медленно", а потеря данных**: `pickCandidates()` строит
`$already` из ВСЕХ строк `ozon_created_cards` без фильтра по `status` — то есть артикул,
однажды упавший на `missing_required_attr:ТН ВЭД коды ЕАЭС`, навсегда выпадает из пула
кандидатов будущих прогонов `ozon:create-card`, даже после того как `resolveHsCode()`
почините. Если решим доводить фолбэк до продакшена — потребуется либо явный повторный
прогон по списку этих артикулов (`--article=`), либо разовая чистка
`ozon_created_cards` от строк с этим `skip_reason` перед следующим прогоном.

### Настоящая причина "Товары не меняются" — оба FBS-склада отключены на стороне Ozon (2026-09-12)

Роман сообщил: в кабинете Ozon (`seller.ozon.ru/app/products`) счётчики те же,
что неделю назад — "В продаже: 0" при 2998 карточках всего. Живой разбор
показал ДВЕ разные причины, только вторая — настоящий блокер:

1. **Остатки в Ozon никогда не передавались.** `ozon:create-card` вызывает
   только `/v3/product/import` (создание карточки) — отдельного вызова на
   остатки (`/v2/products/stocks`) в пайплайне не было вообще. Подтверждено
   живьём: `/v3/product/info/list` для наших карточек стабильно даёт
   `visibility_details.has_stock: false`. Без остатка карточка технически не
   может перейти из "Готов к продаже" в "В продаже", сколько бы их ни
   создавали. **Исправлено**: `OzonClient::updateStock()` (метод
   `/v2/products/stocks`) написан и подключён.
2. **Но сам вызов остатков падает** с `WAREHOUSE_WRONG_STATUS`: "склад в
   архиве или ещё не создан до конца". Проверено `POST /v2/warehouse/list`
   (старый `/v1/warehouse/list` — "obsolete method cannot be used") — на
   аккаунте ДВА FBS-склада ("Офис" `1020005000115886` и "PP1"
   `1020005017847330`, тот же адрес Целинный 5/1, что и склад Halyk), у
   ОБОИХ `"status": "disabled"` и `"first_mile": null` (способ доставки/
   первая миля не настроены). Это и есть корневая причина — даже при
   идеально написанном коде остатки физически некуда положить, пока склад
   в таком состоянии. **Это действие только в личном кабинете Ozon**
   (Склады FBS → настроить/активировать способ доставки), API для этого
   агенту недоступен. `OZON_WAREHOUSE_ID=1020005000115886` уже в `.env`
   (склад "Офис", не "PP1" — тот же принцип "один склад = один ПВЗ", что и
   у Halyk) — как только Роман активирует склад в кабинете, `updateStock()`
   готов к использованию без доработок.

**Склад активирован, бэкфилл остатков запущен (2026-09-15)**: на аккаунте
появился ТРЕТИЙ FBS-склад — `Global_Parts_PP1` (`1020005030298960`),
`status="created"` (не `disabled`) и `first_mile` реально настроен
(`DROP_OFF`). `.env` уже указывает `OZON_WAREHOUSE_ID` на него. Живой тест
подтвердил: `updateStock()` реально проходит (`updated:true`) — блокер из
п.2 выше снят. Написана `ozon:push-stock {--limit=1000}` — бэкфилл остатка
для уже существующих карточек со `status=imported` в `ozon_created_cards`,
у которых остаток никогда не передавался (созданы ДО того, как склад
заработал, и до того как `ozon:check-card-status` стал сам пушить остаток
при переходе в `imported`, см. докблок того файла). Запущена в фоне на
весь бэклог (`--limit=3000`, nohup+disown) вместе с
`ozon:check-card-status --limit=6000` (закрыть зависшие ~5800
`status=submitted`, тоже накопились за то время, пока склад не работал).

**Найден отдельный, более серьёзный блокер — TOTAL_CREATE_LIMIT_EXCEEDED
(2026-09-15)**: пока разбирали бэклог `check-card-status`, обнаружилось,
что подавляющее большинство исторических `status=failed` (6252 из 10533 на
момент находки) несут код `periodic_limit_exceeded` — "исчерпан суточный
лимит на создание товаров, счётчик обнулится в 03:00 по Москве". Это
СУТОЧНЫЙ лимит, сам по себе не блокер (сбрасывается ежедневно) — но живой
тест ОДНОЙ новой карточки (`ozon:create-card --limit=1`, артикул
`OBK-C4H32112`, task_id=5630636739) в тот же день, ПОСЛЕ прохождения
времени сброса (03:00 МСК = 05:00 Астана, уже прошло), всё равно упал —
но уже с ДРУГИМ кодом: `TOTAL_CREATE_LIMIT_EXCEEDED` — "Не получится
добавить товар: вы исчерпали лимит. Редактируйте уже созданные карточки.
Как увеличить лимит". Это уже не суточная, а ОБЩАЯ квота на количество
карточек на аккаунте. **Подтверждено скриншотом Романа из кабинета**
(`seller.ozon.ru/app/items/transfer?tab=generalSettings`, блок
"Увеличение лимита товаров"): **общий лимит 3001, использовано 3001** —
сходится тик-в-тик с нашими 2999 `imported` в БД + пара тестовых карточек,
которые агент отправил в ходе этого же разбора. Два способа поднять:
**автоматически** — лимит растёт в зависимости от суммы продаж (то есть
сам разрешится органически, как только уже созданные 2999 карточек начнут
реально продаваться — а без остатка, который как раз сейчас бэкфилится,
они и не могли продаваться), или **вручную — платная услуга**: минимум от
50 карточек, дешевле за штуку при большем объёме — на скриншоте пример
20 000 карточек по 45₽ = 900 000₽. **Решение Романа 2026-09-15: не
платить, ждать органического роста лимита от продаж** — цена показалась
несоразмерной ("даже смежно немного"), сначала смотрим, сдвинется ли
лимит сам, когда у уже созданных 2999 карточек появится остаток и пойдут
первые продажи. **Вывод: `ozon:create-card`
сейчас создавать НОВЫЕ карточки не может вообще**, пока лимит не поднимется
(само по себе, от продаж — либо Роман решит доплатить). Это НЕ
блокирует `ozon:push-stock`/`ozon:check-card-status` — они не создают
новые карточки, только обновляют остаток/статус уже существующих, и
продолжают штатно работать. Следующий шаг, когда Роман разберётся с
лимитом — просто повторно погнать `ozon:create-card` на оставшийся пул
(текущий `pickCandidates()` и так исключает уже обработанные артикулы,
ничего чинить не нужно, кроме самого лимита на стороне Ozon).

создания карточек" ниже за деталями и найденными по ходу багами). Дальше:
1. Прогнать `php artisan halyk:check-card-status` ещё раз (подождав) — узнать, чем
   закончилась модерация первой тестовой карточки: `SUCCESS`/`REJECT`/`DELETED` и
   комментарий модератора, если он появится. Это первый реальный сигнал о качестве
   пайплайна — особенно важно для `weight/width/height/depth` (сейчас заглушки, см.
   ниже) и для точности attrs-маппинга (есть подозрительные значения, напр. "Левая"
   там, где не факт, что это релевантно — см. раздел ниже).
2. Если первая карточка прошла модерацию нормально — обсудить с Романом, стоит ли
   сразу гнать оставшиеся ~9 (до заявленных 10) реальными (без `--dry-run`), или
   сначала поправить найденные шероховатости в attrs.
3. Роман параллельно вручную чистит мусорные автоперенесённые карточки в кабинете
   `partners.halykmarket.kz/products` (массово выделить → "В архив" → на вкладке
   "В архиве" → "Удалить") — перенос от Halyk встал на 499 карточках с сообщением
   "частично загрузились".
4. После того, как какое-то количество карточек создано — сгенерировать и отправить
   фид (`halyk:generate-xml`, уже реализован) ТОЛЬКО по тому, что реально существует
   как карточка.

Направление **поиск+привязка к существующим карточкам** (`halyk:search-sku`/
`halyk:match`/`halyk:bind`) при этом фактически отставлено — не потому что не
работает (протестировано живьём, работает корректно), а потому что каталог Halyk

Halyk Market — маркетплейс от Halyk Bank, аналог Kaspi Marketplace. Менеджеры Halyk

### Чем отличается от Kaspi — важно
У Kaspi нет self-service загрузки фида: ссылку на XML нужно передавать персональному
менеджеру Halyk Market вручную, который сам настраивает импорт (~раз в час опрос) — это
подтверждено и официальным гайдом, и вики стороннего инструмента MarketRadar. **НО** у
Halyk Market есть отдельный полноценный REST API (`zagruzka-tovarov-po-api` в доках),
который куда ближе к Ozon, чем к статик-фиду Kaspi: реальный upload-эндпоинт с
возвращаемым ID и опросом статуса построчно (successCount/failCount/notMappedCount),
плюс отдельные эндпоинты на поиск/привязку к существующей карточке и на создание новой
карточки с нуля. Разбираться нужно именно в этом API, а не в ручной передаче ссылки
менеджеру.

### Авторизация
OAuth2 client credentials.
- `POST https://halykmarket.kz/gw/auth/token`
- Тело: `{"grant_type":"client_credentials","client_id":"HMM_<БИН>","client_secret":"..."}`
- `client_id` — выдаёт менеджер (формат `HMM_<БИН магазина>`), `client_secret` —
  приходит на почту при включении API.
- Ответ: `access_token` + `token_type=Bearer` + `expires_in=7199` (~2 часа) — токен
  нужно кэшировать и обновлять по истечении (тот же паттерн, что уже есть для
  Shatem-токена в `SparePartControllerTest::getShatemToken()` — `Cache::lock()` вокруг
  `cache()->remember()`, чтобы не долбить auth-эндпоинт на каждый вызов).
- Тестовый контур: `test2.halykmarket.com` / `test2-api.halykmarket.com` (для
  сравнения: prod — `halykmarket.kz` / `api.halykmarket.com`, БЕЗ `test2`).

### Поиск и привязка к существующей карточке (аналог kaspi:parse-sku → kaspi:match → kaspi:bind-products)
1. **Поиск**: `GET /gw/merchant/public/skus/search?q=<название или артикул>&page=&size=`
   → возвращает список кандидатов с `skuId` (главное поле, нужен на следующем шаге),
   `name`, `imageUrl`, `category{id,name,level}`, `marketUrl`.
2. **Привязка**: `PUT /gw/merchant/public/product/remaining/save-and-map-sku`
   Тело: `skuId`, `merchantProductCode` (наш артикул), `city.code`, `price`,
   `points.code` + `points.amount` (склад/остаток), `loanPeriod` (допустимо только
   3/6/12/24). Товар переходит в статус "На продаже".
   **Критично**: привязанный товар обязательно должен присутствовать в каждой
   последующей выгрузке фида, иначе автоматически уходит в архив — прямая аналогия с
   колонкой `bound` в `kaspi_feed_items`, тот же принцип нужно повторить в новой
   таблице под Halyk.

### Загрузка фида (аналог kaspi:generate-xml + отправка)
- **Загрузка**: `POST https://api.halykmarket.com/api/merchant/v1/offers/upload`
  (`multipart/form-data`, поле `file` — путь до XML) → `{"id": 11111}`.
- **Статус**: `GET /api/merchant/v1/offers/upload/status/{id}` →
  `status` (`CREATED`/`PROCESSING`/`COMPLETED`/`FAILED`/`SKIPPED` — последнее означает
  "идентичен предыдущей загрузке, не обработан повторно"), плюс `totalCount`/
  `successCount`/`notMappedCount`/`failCount`/`message`. `notMappedCount` — готовый
  сигнал, какие позиции нужно перепривязать через `save-and-map-sku`.

### Создание новой карточки (для того, что не найдётся поиском — самый трудоёмкий кусок)
Перед созданием доки явно требуют: "убедиться, что такого товара действительно нет в
каталоге" (сначала поиск, создание — только если не нашлось). Полный поток из 6 шагов:
1. `GET /gw/merchant/public/category/search?q=...` — поиск категории **3-го уровня**
   (обязательно самый глубокий уровень, не 1/2).
2. Поиск ID бренда (отдельный эндпоинт, аналогичный по форме категорийному).
3. `GET /gw/merchant/public/form/product/feature?categoryId=<id>` — форма характеристик
   под конкретную категорию: `classAttrAssignmentId`, `classAttrType`
   (`NUMBER`/`ENUM`/`STRING`/`BOOLEAN`), `required`, у `ENUM` — фиксированный список
   `classAttrValues` (значение выбирается, а не вводится свободным текстом).
4. Загрузка фото.
5. Отправка заполненной формы на модерацию.
6. Опрос статуса модерации.

**Почему это отдельная фаза работы, а не "просто ещё один шаг пайплайна"**: категории,
бренды и значения характеристик у Halyk — **своя таксономия**, не совпадающая с тем, что
есть в `parts_catalog` со скрейпинга карточек Kaspi. Нужен маппинг: наши
`category_top_code`/`category_group_code` → `categoryId` Halyk, наши бренды → `brandId`
Halyk, наши произвольные строки характеристик → конкретные `classAttrValueId` из ENUM.
Это разовая (и потом поддерживаемая) работа сопоставления справочников, качественно
сложнее, чем поиск+привязка к уже существующим карточкам.

### Архитектура пайплайна (по образцу Kaspi)
```
halyk:search-sku   → halyk:match → halyk:bind →
halyk:generate-xml → halyk:upload-feed → halyk:check-feed-status   [обе ветки реализованы]
                                              ↑
                              halyk:create-card (для notMappedCount / не найденных поиском)
```
Первая ветка (поиск → сопоставление → привязка) выбрана стартовой сознательно —
`halyk:create-card` вынесен в отдельную фазу (маппинг категорий/брендов/характеристик,
см. выше — качественно более трудоёмкая задача). Стрелка от `halyk:check-feed-status`
к `halyk:create-card` — пока идея, не реализована: `notMappedCount` из статуса
загрузки фида технически мог бы стать источником кандидатов для create-card, но
сопоставление "какая именно позиция попала в notMappedCount" по одному только
агрегированному числу не восстановить — нужен другой способ узнать список.

### Простой статик-фид (реализовано И протестировано живьём 2026-08-21)
Пока с API-кредами тормозили, менеджер Halyk попросил прямо то же, что просят у Kaspi —
"ссылку, где лежит фид". Сделали по аналогии: `halyk:generate-xml` (по образцу
`kaspi:generate-xml`) генерирует `public/halyk_feed.xml` из `kaspi_initial_products`
(весь каталог целиком, ~95к позиций на 2026-08-21) по XSD-схеме `halyk_market`
(разобрана выше) — `XMLWriter`, порядок `model → brand → stocks → price → loanPeriod`.
Та же защита `EXCLUDED_NAME_PATTERNS`, что и в `kaspi:generate-xml` (проблемные
MEYLE-карточки по названию).

**Важный урок дня**: первая версия писала остаток атрибутом `stockLevel` на
`<offer>` — по XSD это формально валидно (`<stocks>` там `minOccurs="0"`), но Halyk
на практике НЕ считает товар доступным к покупке без полноценного
`<stocks><stock storeId=.../></stocks>`, привязанного к реальной точке продаж (сама
XSD-схема технически разрешает голый атрибут как альтернативу — их бэкенд, по факту,
требует другое). Обратная связь от менеджера была буквально "нет элемента stocks"
уже ПОСЛЕ того, как в файле формально появился валидный XML — сбивало с толку, пока
не проверили именно семантику приёмки, а не только XSD-валидность. Финальная версия:
`<stock storeId="Global_Parts_pp1" isPP="yes" available="yes" stockLevel="N"/>`
(`isPP="yes"` — наш единственный склад одновременно и пункт выдачи).
- `HALYK_MERCHANT_BIN`/`HALYK_STORE_ID` (или `HALYK_POINT_CODE`, тот же код) —
  теперь настоящие значения в `.env` (см. сводку в начале раздела). Без них команда
  пишет явные заглушки (`"УКАЖИТЕ_БИН"`/`"УКАЖИТЕ_STORE_ID"`) и предупреждает в
  консоли — Halyk такой фид не примет.
- Файл гитигнорится (`public/halyk_feed.xml` в `.gitignore`, та же причина, что и у
  `kaspi_feed.xml` — сгенерированный артефакт, история с git deploy уже поймала эту
  ошибку один раз, см. коммит "Stop tracking generated kaspi_feed.xml in git").
  Генерируется КОМАНДОЙ НА СЕРВЕРЕ (`php artisan halyk:generate-xml`), не пушится
  готовым файлом — агент может задеплоить код команды через git push, но сам файл
  на проде появляется только после ручного запуска команды (прямого доступа к
  серверу/SSH у агента нет, `kaspi:generate-xml` работает по тому же принципу и
  тоже не стоит на автоматическом расписании, см. `routes/console.php`).
- Как только файл появится на сервере — он живой по адресу
  `https://shop.globalparts.kz/halyk_feed.xml`, ссылку отправить менеджеру Halyk.
- Это НЕ то же самое, что `POST /offers/upload` — тот путь (реальный upload-эндпоинт
  с опросом статуса) реализован и проверен живьём 2026-08-25, см. ниже.

### Загрузка фида через API (реализовано И проверено живьём на боевом фиде 2026-08-25)
Команды: `halyk:upload-feed {--no-regenerate}` (перегенерирует `halyk_feed.xml` и
грузит через `HalykMarketClient::uploadFeed()`) и `halyk:check-feed-status {id}
{--wait}`. Документация — отдельное gitbook-пространство "Anyqtama" (см.
"Документация" выше), страница "Получение статуса обработки прайс-листа".

**Важная деталь, не работающая без неё**: `GET .../offers/upload/status/{id}` ловит
`415 contentTypeNotSupported`, если явно не поставить `Content-Type:
application/json` — на GET без тела это неочевидно, но их дока прямо требует этот
заголовок и на чтение, не только Accept. Метод `getFeedUploadStatus()` его теперь
ставит.

Хост загрузки/статуса — ОТДЕЛЬНЫЙ от `/gw/merchant/public/...` (тот на
`halykmarket.kz`): для `/api/merchant/v1/offers/upload...` — `api.halykmarket.com`
(прод) / `test2-api.halykmarket.com` (тест), см. `HalykMarketClient::apiBaseUrl()`.
Токен тот же (OAuth client credentials), работает на обоих хостах.

**Первая живая загрузка боевого фида (95 039 позиций)**:
```
status=UPLOADED_WITH_ERRORS total=95039 success=501 notMapped=52469 fail=42069
```
**Повторная загрузка после фикса дублей названий (95 085 позиций, тот же день)**:
```
status=UPLOADED_WITH_ERRORS total=95085 success=505 notMapped=92207 fail=2373
```
Это и объясняет то, что Роман видел в кабинете как "фид падает на ~500 позициях" —
на самом деле наоборот: **успешно проходят только ~500**, а не падают ~500. Разбор:
- `notMappedCount` (52 469, по их доке — "товар не найден на площадке") — ожидаемо
  большой: своего каталога на Halyk у нас почти нет (в кабинете было всего 350 "В
  архиве" + что успел создать `halyk:create-card`), фид пытается автосопоставить
  каждую позицию с уже существующей карточкой по (предположительно) `model`+`brand`
  и не находит пару почти нигде.
- `failCount` (42 069, 44% от всего фида) — это НЕ "не нашли пару", а настоящий сбой
  валидации на их стороне. Через API причину не узнать (только агрегированные
  счётчики, дока прямо говорит "для деталей — обращаться в поддержку") — **но
  Роман достал причину из самого кабинета Halyk** (вкладка загрузки фида,
  список отклонённых товаров построчно с текстом ошибки — API этого не отдаёт,
  UI отдаёт): **"Название товара дублируется в данном файле"**. Проверено:
  `kaspi_initial_products.title` у многих позиций — общий шаблонный текст без
  привязки к бренду/артикулу (живой пример: `"Пружины подвески | перед
  прав/лев |"` — 254 РАЗНЫХ товара с одинаковым названием, `"Ролик натяжной
  ремня ГРМ"` — 120). 95 085 строк, но только 60 306 уникальных `title` —
  разрыв ~34.8к, тот же порядок величины, что и failCount.

  **Исправлено 2026-08-25**: `GenerateHalykXml` теперь пишет в `<model>` не
  голый `title`, а `title — БРЕНД АРТИКУЛ` — (sku, brand) уникальны по
  построению (unique index) на всех 95085 строках, так что дубли исключены
  математически, не эвристикой. Повторная загрузка того же фида подтвердила
  фикс живьём: **failCount упал с 42069 до 2373** (−94.6%), `notMappedCount`
  вырос до 92207 (ожидаемо — то, что раньше падало как "дубль названия",
  теперь честно проходит валидацию и попадает в "не нашли пару", а не в
  ошибку). Оставшиеся 2373 сбоев — уже другая, не выясненная причина,
  вероятно то же самое разбирать через кабинет, если понадобится.
- Подтверждено эмпирически: загрузка фида ДЕЙСТВИТЕЛЬНО пытается
  автоматически сопоставлять/привязывать позиции к существующим карточкам (не
  только создаёт новые предложения) — идея "закинуть весь фид и отследить
  notMappedCount, чтобы понять, что реально не хватает" (обсуждали с Романом)
  подтверждена и технически, и по факту: после фикса дублей `notMappedCount`
  (92207) — это и есть честный список "нет на Halyk вообще", ровно то, что
  нужно для следующего шага с `halyk:create-card`.
- **`halyk:check-feed-status --wait` изначально зацикливался** — ждал
  терминальный статус в поле `status` (по доке: COMPLETED/FAILED/SKIPPED), а
  реальный ответ полностью обработанного фида несёт `status:
  "UPLOADED_WITH_ERRORS"` (конкретный исход) + `message: "COMPLETED"`
  (стадия обработки) — две разные вещи в двух разных полях. Исправлено —
  терминальность теперь по `message`.

### Пайплайн создания карточек (реализовано И проверено живьём 2026-08-22)
Команды: `app/Console/Commands/Halyk/HalykCreateCardCommand.php`
(`halyk:create-card {--limit=10} {--article=} {--dry-run}`) и
`HalykCheckCardStatusCommand.php` (`halyk:check-card-status`). Новая таблица
`halyk_created_cards` — по строке на попытку (`status`: `skipped`/`submitted`/
`moderation`/`reject`/`deleted`/`success`/`error`, плюс `skip_reason`/`comment`).

**Источник кандидатов**: `parts_catalog` ⋈ `supplier_offers` через уже существующий
`App\Services\SupplierOfferPricer` (тот же джойн `article_normalized`/
`brand_normalized`, что и в публичном каталоге сайта) — только реально в наличии
(`offer.stock > 0`), с фото, ещё не обработанные.

**Поток на каждую карточку**:
1. `searchSku` + строгая проверка по границе токена (портирована из `halyk:match`,
   защита от бага BW0010) — если уже есть на Halyk, пропуск
   (`already_exists_on_halyk`). На практике очень многие ходовые артикулы (свечи NGK
   и т.п.) уже там есть от автопереноса — реально до "создания" в тесте 2026-08-22
   доходила примерно 1 из 5-6 позиций.
2. Категория 3-го уровня. **Важный нюанс, не очевидный из документации**: наши
   колонки `category_top_title`/`category_group_title` — это только 2 верхних уровня
   из полного `characteristics.category_path` со скрейпинга Kaspi, а у Kaspi путь
   часто ГЛУБЖЕ (напр. "Свечи зажигания" — уже 3-й уровень у Kaspi, отдельно ни в
   одной колонке не хранится). Ищем по всем элементам `category_path` от самого
   глубокого к самому верхнему, пока не найдём совпадение 3-го уровня у Halyk.
3. Бренд — `searchBrand`, точное совпадение по имени в приоритете.
4. Форма характеристик (`getCharacteristicsForm`) + попытка заполнить ОБЯЗАТЕЛЬНЫЕ
   атрибуты значениями из `parts_catalog.characteristics` (структура та же, что и в
   `partInfo` — `specifications[].features[].featureValues[].value`). Если
   обязательный атрибут не удаётся найти — карточка целиком пропускается
   (`missing_required_attr:...`), не отправляем с дырами в обязательных полях.
5. Фото — Halyk принимает ТОЛЬКО файлы (multipart), не ссылки: скачиваем реальные
   файлы с Kaspi CDN и грузим их. Заявленные в их доке требования (белый фон,
   строго квадрат 500-2000px, минимум 3 шт) **на практике не проверяются самим
   upload-эндпоинтом** — проверено вживую: приняли фото 403×500 (не квадрат, ниже
   минимума по ширине) с HTTP 200 без единой жалобы. Похоже, это soft-guidance для
   модерации, а не hard-валидация при загрузке — так что грузим что реально есть
   (обычно 1 фото на карточку), а не блокируемся на препроцессинге картинок заранее.
6. Отправка на модерацию (`submitForModeration`) → успех даёт
   `{"productDraftStatus":"CHECK","id":<int>}`.

**Два реальных бага, найденных живым тестированием (не вычислить по одной
документации)**:
- `GET /category/search` возвращает **массив ПУТЕЙ** (breadcrumb от 1-го уровня до
  найденного узла), а не плоский список категорий — первая версия кода ожидала
  плоский список и падала с "Undefined array key". Поправлено — разворачиваем все
  пути, ищем узел `level===3` среди всех.
- `POST /draft/product/moderation` отвечает **`HTTP 202 Accepted`** на успех, а не
  200 — `Illuminate\Http\Client\Response::ok()` в Laravel проверяет строго `=== 200`,
  из-за чего реально успешная отправка (карточка ушла в очередь, `id` есть в ответе)
  ошибочно репортилась как провал. Заменили на `->successful()` (весь диапазон 2xx)
  во ВСЕХ методах `HalykMarketClient` на всякий случай, не только в этом одном —
  остальные (`bindSku` особенно, PUT-запрос) живьём ещё не проверялись, могли бы
  преподнести тот же сюрприз.

**Статус первого живого теста**: артикул `349067` (KYB, амортизатор задний) — фото
загружено, категория/бренд найдены, отправлено на модерацию, подтверждён статус
`MODERATION` в очереди через `halyk:check-card-status`. **Обновлено 2026-08-24**: обе
пилотные карточки (349067 и 334270, обе KYB) прошли модерацию — `SUCCESS`. Это и стало
сигналом идти на масштаб (см. ниже).

**Первый боевой прогон на 1000 позиций (2026-08-24, ночь)**: Роман запустил
`halyk:create-card --limit=1000` (не dry-run) без присмотра на всю ночь — процесс
поднят через `nohup`+`disown` на его же десктопе (держит фон сам, отдельного сервера
под это нет), лог в `storage/logs/halyk_batch_*.log`. Прямо по ходу первого запуска
нашлись и исправлены два бага:
1. `flattenCharacteristics()` брала только `featureValues[0]` на атрибут — деталь,
   подходящая под НЕСКОЛЬКО моделей (напр. Volvo 850/S70/V70 одним радиатором), падала
   целиком, если не совпадало именно первое значение, хотя второе/третье могло
   совпасть с ENUM Halyk. Исправлено — `matchEnumOption()` теперь перебирает все
   значения по очереди.
2. У `pickCandidates()` не было сортировки — строки одного бренда лежат в БД подряд
   (одна партия скрейпа), и при системном пробеле в характеристиках у конкретного
   бренда весь `--limit` мог уйти на один и тот же непроходной участок. Живой случай:
   **1151 SAT-радиатор** подряд без "Модель автомобиля" в характеристиках (только
   "Марка автомобиля" — Kaspi в этой категории, похоже, никогда её и не собирала,
   `description` тоже `NULL`, взять модель неоткуда). Добавлен `inRandomOrder()`.

**SAT-радиаторы (и, вероятно, похожие категории) — открытый вопрос, не блокирует
текущий прогон**: 1151 позиция не может быть создана автоматически прямо сейчас —
источника данных по модели авто нет ни в `characteristics`, ни в `description`. Три
варианта на будущее: (а) оставить как есть, вернуться отдельным заходом; (б) донабить
руками для самых ходовых; (в) проверить, не забрал ли `ScrapeKaspiCardsCommand` не все
поля с живой карточки Kaspi — если модель там всё же есть, стоит точечно
пересобрать именно этот срез. Ничего не решено, следующий шаг — по ситуации.

**Известные осознанные пробелы (не скрыты, задокументированы в коде)**:
- **Вес/габариты — 0% покрытия** во всём `parts_catalog` (проверено на всех 56647
  публичных карточках) — но `weight`/`width`/`height`/`depth` есть в форме
  submission и выглядят как обязательные (присутствуют в примере из документации).
  Сейчас — грубые дефолты-заглушки (`DEFAULT_WEIGHT_KG=0.5`, `WIDTH/HEIGHT/DEPTH_CM=15`
  в `HalykCreateCardCommand`) под "среднее мелкое автозапчастье". Если модерация
  начнёт заворачивать карточки конкретно из-за этого — придётся либо считать по
  категориям, либо вводить руками.
- **attrs-маппинг — простое совпадение по имени/значению**, не строгая таксономия.
  На реальном тесте (349067) в attrs проскочило подозрительное значение "Левая"
  (сторона) для амортизатора, где это не факт что релевантно, и один и тот же бренд/
  модель ("Volkswagen"/"Tiguan") дважды под разными `id` (вероятно, форма Halyk
  содержит два похожих по смыслу атрибута в разных блоках) — не обязательно ошибка,
  но стоит свериться с реальным результатом модерации, прежде чем масштабировать на
  много карточек разом.

**Модерация 262 карточек из первого боевого прогона — чёткий паттерн по категориям
(2026-08-25)**: 66 из 66 SUCCESS — **все до единой "Амортизаторы"**; 190 REJECT —
ни одного амортизатора, размазано по 30 другим категориям (тормозные диски 39,
катушки зажигания 18, крепление двигателя 17 и т.д.), у всех одна и та же общая
причина отказа "Неверные характеристики" (в кабинете Halyk — тот же шаблонный
текст, детальнее не расписано); 4 амортизатора + 2 зеркала — DELETED (дубли).
Вывод: пайплайн реально проверен и работает пока только на категории
"Амортизаторы" — там обязательные поля Halyk (Марка/Модель/Год авто, Сторона,
Перед/Зад) хорошо ложатся на общий блок характеристик Kaspi. Остальные категории,
скорее всего, просят другие, специфичные для категории поля (диаметр/толщина у
дисков и т.п.), которых нет в общем блоке — нужно разбирать `getCharacteristicsForm`
по каждой категории отдельно и сверять с тем, что реально есть у Kaspi.

**Добавлен `--category=` фильтр** (`halyk:create-card --category="Амортизаторы"`) —
сужает кандидатов на конкретную категорию 3-го уровня (`characteristics->
category_leaf_title`). Пока не разберём attrs-маппинг по остальным категориям —
боевые прогоны стоит гонять с этим фильтром, не вслепую на весь `parts_catalog`.

**Привязка вместо пропуска при дубле (2026-08-25)** — раньше найденный строгим
поиском дубль просто пропускался (`already_exists_on_halyk`). Роман прислал
реальный комментарий с уже удалённой (постфактум, после отправки) карточки:
*"Такая карточка уже существует... Просьба привязаться к существующей карточке
товара"* — прямая рекомендация от Halyk, не наша догадка. Теперь `processCard()`
при найденном дубле сразу вызывает `bindSku()` (то же `save-and-map-sku`, что и в
`halyk:bind`) с `skuId` найденной карточки — новые статусы `bound`/`dry_run_bind` в
`halyk_created_cards`. `merchantProductCode` — та же приватная логика
(`resolveMerchantProductCode()`), что и у новых карточек, не голый артикул.

**694 карточки, удалённые Halyk как дубли — почему их нельзя просто
пересоздать (2026-08-31)**: разбор скриншота Романа из кабинета Halyk
("Такая карточка уже существует... Колодки PATRON... шрус PCV1745")
показал, что `halyk:check-card-status` не запускался ~5-6 дней на ~2800
зависших строк `submitted`/`moderation` — после разового фикса падения
всего батча на первой же `ConnectionException` (см. `9ecc88a`) и
повторного прогона реальная картина: `deleted: 694` (совпадает с "600 с
чем-то" у Романа). Найдена и исправлена одна реальная причина дублей:
`findStrictMatch()` сравнивал артикул только без дефисов, не без пробелов
— Halyk иногда пишет название карточки с пробелом между буквенным
префиксом и цифрами ("PDS 1961" вместо нашего "PDS1961"), из-за чего
реальный дубль не находился и создавался заново. Фикс (убрать оба
символа при сравнении) подтверждён живьём на одном случае, но на выборке
из 6 карточек сработал только для 1 — для большинства 694 совпадения в
`searchSku` по-прежнему нет.

Ретрай оставшихся (не dry-run, через `--article=`) вскрыл вторую, более
фундаментальную проблему: **~70-90% ретраев падают с `HTTP 400
draft_with_product_code_already_exists`** на самом `submitForModeration`,
даже когда `findStrictMatch()` ничего не находит через `searchSku`. Вывод:
когда Halyk помечает карточку "удалено" как дубль в кабинете, внутренняя
резервация `merchantProductCode` за черновиком остаётся занятой на их
стороне — это НЕ то же самое, что "код свободен для новой заявки". У
нашего клиента нет эндпоинта на список/удаление чужих черновиков (в доке
такого не описано) — реальный фикс потребовал бы либо документированного
эндпоинта "удалить/посмотреть черновики" от самого Halyk, либо смены
`merchantProductCode` при повторной отправке (последнее рискованно —
меняет то, как `resolveMerchantProductCode()` вообще держит связь наш
SKU ↔ их код). **Решение (по прямому указанию Романа "если непонятки —
скипаем"):** эти 694 (плюс отдельно попавшиеся под этот же 400 при
ретрае) оставлены как есть — `halyk_created_cards` хранит их с
`status=failed` и `comment` с текстом ошибки, `pickCandidates()` по
умолчанию их и так исключает из будущих батчей (`whereNotIn('article',
$already)`). Если Halyk когда-нибудь подтвердит способ снять черновик
или откроет эндпоинт на это — можно точечно повторить именно эти
статьи.

Побочная находка при том же ретрае: `searchSku`/`searchCategory`/
`searchBrand`/`getCharacteristicsForm` на `timeout(15)` давали ~49%
падений чистым `cURL error 28` (таймаут, не HTTP-ошибка — `retry(...,
throw: false)` его не гасит, см. уже описанный паттерн у
`getDraftStatus`/`check-card-status` выше). Поднято до `timeout(25)` —
на следующей выборке из 21 карточки таймаутов уже 0.

**Настоящая причина основной массы "already exists" дублей найдена
2026-09-01** — выросло до 2450+ штук в кабинете, Роман получил от
поддержки Halyk прямой ответ: их система сама сначала пытается
привязаться к существующей карточке и только если не находит —
создаёт новую (ровно наша логика в `processCard()`), и на вопрос
"почему тогда не привязывается" поддержка ответила "запрос в работе,
ждите" — то есть сами не смогли объяснить сразу. Разобрано на
конкретном примере с ЕГО скриншота (артикул `CR0297`, бренд `CTR`,
"CTR рулевая тяга CR0297", halyk_product_id=748328, отклонён с "Такая
карточка уже существует"): прямой запрос к их `GET
/gw/merchant/public/skus/search` с ТЕМ ЖЕ запросом, что шлёт наш код
(`"CTR CR0297"`), и ещё 4 вариациями (включая точное название карточки
из их же текста отказа) — везде 0 результатов. Но сырой HTTP-ответ (в
обход обёртки `HalykMarketClient::searchSku()`, которая раньше тихо
превращала любую не-2xx ошибку в `[]` — неотличимо от настоящего "ничего
не найдено") показал: `HTTP 504 "upstream request timeout"`,
воспроизведено трижды подряд стабильно. `GET
/gw/merchant/public/category/search` в тот же момент — тоже 504.
Живой прогон `halyk:create-card` в это время в основном получал
"категория не найдена" (безопасный побочный эффект того же 504 на
category/search — не создаёт дублей, просто зря съедает кандидата) —
но до этого открытия часть из 2450+ "already exists", скорее всего,
как раз и была: `searchSku()` тихо вернул `[]` из-за такого же 504 в
момент проверки на дубль, `processCard()` посчитал что дубля нет и
создал карточку, которая на самом деле уже существовала.

**Исправлено** — `searchSku()`/`searchCategory()`/`searchBrand()`/
`getCharacteristicsForm()` в `HalykMarketClient` теперь бросают
исключение на не-2xx статус вместо тихого `[]`. `processCard()` и так
оборачивает обработку каждой карточки в try/catch — теперь сбой поиска
корректно останавливает карточку как `status=error` вместо того чтобы
молча решить "дубля нет" и создать его заново. Проверено живьём во
время самого сбоя (2026-09-01): артикул `JDA0128` — раньше тихо пошёл
бы дальше, теперь `⨯ исключение: Halyk skus/search недоступен: HTTP 504`,
записан как `error`, карточка не создана.

**Оверnight-заливка остановлена вручную 2026-09-01** — на момент
обнаружения 504 гнать дальше не было смысла (только тратит кандидатов
на ложные "категория не найдена"). Возобновлять, когда их API
восстановится — фикс уже на месте, повторный сбой того же рода больше
не создаст дублей, просто честно упадёт в `error` и попадёт под
следующий ретрай.

**Роман начал переписку с поддержкой Halyk с этими фактами** (не наша
догадка, живой воспроизводимый 504 на их эндпоинте) — если ответят с
дополнительными деталями (когда чинят, есть ли лимиты на наш аккаунт,
и т.д.) — учесть при следующем возврате к теме.

### `photo_upload_failed` — реальная причина найдена, диагностика починена (2026-09-19)

Рост вотчдога к 2026-09-19 заметно замедлился — 56191 строк в
`halyk_created_cards`, но `skipped` (24676) стал доминирующим статусом.
Разбор по `skip_reason` показал вторую по величине причину после давно
известного `missing_required_attr:Модель автомобиля` (7439) —
`photo_upload_failed` (4452), которая раньше нигде не была
задокументирована как отдельная проблема, потому что `comment` у этих
строк был пустым: `HalykMarketClient::uploadPhotos()` тихо возвращал `[]`
на любой не-2xx ответ, той же породы баг, что уже чинили для
`searchSku`/`searchCategory`/`searchBrand`/`getCharacteristicsForm`
2026-09-01 — но именно этот метод тогда пропустили.

Живой репродукцией через tinker (`ReflectionMethod` на приватные
`token()`/`baseUrl()`, ручной multipart POST на
`/gw/merchant/public/file/image/upload/multiple`) на конкретной падающей
карточке (`D6024M`, фото с Kaspi CDN) получен реальный ответ: **HTTP 409
`image_size_not_in_range`**. Проверка `getimagesizefromstring()` на том
же файле — **260×380px, 17075 байт**. Это НЕ противоречит более раннему
выводу от 2026-08-22 о том, что upload-эндпоинт "не проверяет строго
500-2000 квадрат" (тогда 403×500 прошло с HTTP 200) — судя по всему,
эндпоинт проверяет размер, просто порог ниже задокументированного
500-2000, и 260×380 под него не попадает, а 403×500 попадает. Причина на
нашей стороне — часть карточек `parts_catalog` унаследовала от скрейпинга
Kaspi только маленькое превью, крупного варианта того же фото в скрейпе
не сохранилось.

**Исправлено**: `uploadPhotos()` в `HalykMarketClient` теперь бросает
исключение с реальным HTTP-статусом и телом ответа вместо тихого `[]`
(тот же приём, что и у остальных методов). `HalykCreateCardCommand`
ловит его и пишет специфичную причину в `skip_reason`
(`photo_upload_failed:image_size_not_in_range` вместо общего
`photo_upload_failed`) — новые попадания в эту категорию теперь
диагностируемы без ручного воспроизведения через tinker. Старые 4452
строки остались с общим `skip_reason` (не пересчитывались задним числом).
Автоматического фикса самого ограничения (взять фото покрупнее) не
внедрено — источника более крупной версии этих конкретных изображений в
`parts_catalog` сейчас нет, следующий шаг по объёму — оценить, какую
долю 4452 можно закрыть донабором фото, когда дойдут руки.
