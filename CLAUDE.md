# Global Parts — Контекст проекта для агента

Этот файл — справочник архитектурного и бизнес-контекста для in-editor агента.
Обновляйте его по мере крупных изменений в пайплайне.

## О проекте

Global Parts (shop.globalparts.kz) — интернет-магазин автозапчастей в Астане, Казахстан.
Модель: asset-light dropshipping от ~10 поставщиков (Rossko, Shatem, Interkom, ForumAvto,
TISS и др.) с доставкой день-в-день/на следующий день как ключевым конкурентным
преимуществом. Единственный разработчик и оператор — Roman.

Каналы продаж: Kaspi Marketplace (основной), собственный сайт, 2GIS, OLX, повторные/
реферальные заказы. Стек: Laravel/PHP/MySQL.

## Архитектура Kaspi-пайплайна

Основной поток команд:
```
prices:fetch → offers:aggregate → kaspi:match → kaspi:reprice →
kaspi:sync-feed → kaspi:feed-cleanup → kaspi:generate-xml
```
Еженедельно (поиск новых карточек): `kaspi:parse-sku` → `kaspi:bind-products`

### Ключевые таблицы
- `kaspi_initial_products` — неизменяемый источник истины, репрайсинг никогда его не трогает
- `supplier_offers` — слой агрегации, `UNIQUE KEY (sku, supplier_name, brand)`
- `kaspi_competitors` — конкурентные офферы по позициям
- `parts_catalog` — используется для подготовки Ozon-фида (скрейпинг публичных карточек Kaspi)
- `kaspi_feed_items` — колонка `bound` отмечает привязанные к мастер-карточкам товары

### Важные классы/команды
- `MatchKaspiSkuCommand.php` — матчинг по артикулу; здесь же константа `DISABLED_SUPPLIERS`
  для временного отключения поставщика без потери данных (сейчас используется для ForumAvto)
- `AggregateSupplierOffersCommand` — партиционирует офферы по `(sku, brand)`, не просто `sku`;
  здесь же `EXCLUDED_SKUS`, `BRAND_ALIASES` (напр. `lemfoerder`/`lmi` → `lemforder`),
  `QTY_OVERRIDE_KEYWORDS`, `QTY_OVERRIDE_ARTICLES`, `FIXED_COST_KEYWORDS`
- `RepriceKaspiCommand` — динамический репрайсинг; anomaly detection блокирует только
  понижение цены при `$flag === 'risk'`, повышения не блокирует
- `KaspiPriceCalculator` — `COMMISSION=0.125`, `TAX=0.04`, `FEES_DIVISOR=0.835`;
  прогрессивная маржинальная шкала (50к-120к сегмент — 35%, 120к+ — 34%),
  `MIN_ABS_MARGIN` — абсолютный пол в тенге, `min_margin_dumping` сегмент — намеренно
  ~15% каталога с минимальной маржой для конкурентного покрытия
- `GenerateKaspiXml` — здесь `EXCLUDED_NAME_PATTERNS`; XML namespace `xmlns="kaspiShopping"`,
  порядок элементов строго `model → brand → availabilities → price`
- `KaspiFeedCleanupCommand` / `deactivateStaleFeedItems()` — деактивация устаревших/
  осиротевших офферов
- `SlugHelper::brandToSlug()` — полная транслитерация кириллических брендов, обязателен
  `?string` type hint (NULL brand ломал слаги и давал 5xx)

### Матчинг: важный баг и фикс
Короткие артикулы (напр. `BW0010`) матчились по substring на карточки для `BW0010-07-2`,
что вызывало продажи ниже себестоимости. Исправлено: `normalizeArticle()` + word-boundary
regex вместо `str_contains()`, плюс fallback-цикл, постепенно упрощающий поисковый запрос
Kaspi при сохранении строгой фильтрации по артикулу.

## Поставщики — особенности парсеров

- **Kulan** (`kulanoil.kz`) — только колонка "Нур-Султан", `preorder_days=0`
- **ZakazAutoKostanay** — имя файла содержит `zakazauto` + `kostanay`/`kst`, `preorder_days=7`
- **Tstarter** — файл `Astana_ostatki_Tstarter`, 6 колонок, цены в KZT несмотря на
  заголовок "руб"
- **Interkom** — multi-sheet xlsx (`MultiSheetParserInterface`), `.xls` ~18MB падает
  тихо — вероятно memory/timeout при `SimpleXLS::parse()`
- **ForumAvto** — два парсера LP/GP; GP-поставщик удалён из БД полностью, LP реактивирован;
  сейчас LP временно отключён через `DISABLED_SUPPLIERS`
- **Phaeton/Shatem** — детекция приоритизирует `bodyLower` (тело письма) над `From`
  заголовком, т.к. письма часто пересылаются вручную
- **TISS** — API иногда возвращает пустой `offers` при реальном наличии на сайте
  (открытая проблема, см. ниже)

## Открытые технические задачи

1. **AdminPanelController — расхождение в графике**: `getDataByMonths()` /
   `groupOrdersWithStatsByPeriod()` за сентябрь 2025 показывает 10,550,437 вместо
   реальной суммы в БД 10,985,633. Следующий шаг: логировать `array_keys($stats)`,
   похоже на дублирующиеся ключи периода из-за локали в `translatedFormat`.

2. **TISS API пустые offers**: сайт TISS показывает реальный остаток, API — пустой
   массив. Следующий шаг: перетестировать на артикуле с подтверждённым наличием
   день-в-день, расширить лог `raw_body` до ~10000 символов, сравнить полный JSON
   с распарсенным количеством.

3. **Каталог на главной — блок «Популярные категории»**: реализовано
   (2026-08-10), ждёт визуальной проверки Романом на живом сайте. Публичный
   каталог на `parts_catalog`: `CatalogController` (`catalog.category` /
   `catalog.group` / `catalog.show`, роуты `/catalog/{topSlug}[/{groupSlug}]` и
   `/catalog/card/{id}`), 3-уровневая категоризация из `characteristics->
   category_path` (топ — `category_top_code/title/slug`, группа —
   `category_group_code/title/slug`, обе бэкфилленные миграциями). Главная
   берёт топ-6 категорий по `COUNT(*)` (`HomeController::index()`). Публичные
   запросы жёстко фильтруют `scrape_status=done AND name IS NOT NULL` — так
   тонкий контент не попадает в публичный каталог вообще (см. GSC-задачу
   ниже). Пока НЕ связано с `GlobalProductController`/`/product/{brand}/
   {article}` (живая цена у поставщиков через SparePartController) — по
   решению Романа это будет отдельным будущим шагом, когда
   `GlobalProductController` тоже начнёт смотреть в `parts_catalog`. Детали,
   что доделано не до конца (иконки не для всех топ-категорий, SEO-слаг в URL
   карточки) — см. `PROGRESS.md`.

   **Цены и «Добавить в корзину» (2026-08-10)**: каталог живой, с ценами и
   покупкой прямо в сетке и на карточке. Источник цены — `supplier_offers`
   (ежедневно свежий пайплайном `prices:fetch → offers:aggregate`), НЕ
   `global_catalog` (у той таблицы цены зависли на 2026-05-20, 3 месяца —
   осознанно не взяли, показывать такое как актуальную цену для покупки —
   риск продать не по той цене). Джойн по `article_normalized`/
   `brand_normalized` — покрытие 91% карточек. Для быстрого индексного джойна
   у `supplier_offers` появились generated-колонки `sku_normalized`/
   `brand_normalized` (миграция
   `2026_08_10_000002_add_normalized_columns_to_supplier_offers_table`) — без
   индекса тот же джойн через `REGEXP_REPLACE` "на лету" стоил 300-800ms на
   страницу, с индексом — ~13ms.

   Наценка — `SparePartController::setPrice()`, **НЕ**
   `KaspiPriceCalculator::calculate()` (первая версия ошибочно использовала
   именно его). `KaspiPriceCalculator` зашивает комиссию Kaspi (12.5%) и
   логистику Kaspi Доставки — это верно для товаров, реально продающихся на
   Kaspi Marketplace, но каталог на сайте — прямая продажа, этих издержек нет.
   С Kaspi-калькулятором цена в каталоге получалась заметно выше, чем на ту
   же позицию в обычном поиске сайта — риск подрыва доверия при сравнении
   клиентом. `setPrice()` — обычный метод `SparePartController` (не static,
   но без конструктора с сайд-эффектами, безопасно поднимать
   `new SparePartController()` только ради вызова), и он же учитывает роль
   текущего пользователя (`common`/`opt`/`admin` — опт получает -7%, админ
   свою шкалу через `App\SetPrice::setPriceForAdmin()`), как и в обычном
   поиске — так и должно быть, каталог не исключение.

   Кнопка "Купить" переиспользует существующий sitewide
   `.api-buy-btn`-обработчик (`public/js/master.js`) и `POST /cart/add-api`
   (`GlobalProductController::addToCartApi`, класс `App\Cart`) — корзина та
   же, что и везде на сайте, ничего параллельного не заводили.

   Побочная находка при работе с этой задачей: в `parts_catalog` есть колонки
   `kaspi_category_path` и `ozon_category_id`, добавленные мимо Laravel-миграций
   (ни в репо, ни в `database/migrations.tar.gz` файла для них нет) — схема
   разошлась с историей миграций, `migrate:status` этого не покажет.

## ERP (в разработке, ~95%)

Модуль расчётов: кредиторка/дебиторка, cash flow, взаиморасчёты. Есть баг в дашборде
на сценарии возврата — план перед go-live: сначала выписать на бумаге все сценарии
(наличная продажа, отложенная выплата Kaspi, поставка в рассрочку, возврат от клиента/
поставщику, частичная оплата, личное изъятие, фиксированные расходы), сверить ожидаемые
цифры, протестировать каждый на локальной БД с truncate между прогонами, только потом
заносить исторические остатки.

## Ozon — план экспансии

Каталог уже собран скрейпингом карточек Kaspi (`ScrapeKaspiCardsCommand`, ~50к карточек,
таблица `parts_catalog`). Остатки актуальны (Астана). Пайплайн генерации фида аналогичен
Kaspi. API-загрузка протестирована, модерация проходит быстро. География FBS: Россия,
Киргизия, Беларусь, Армения. Основной риск — штрафная сетка за просрочку доставки
(4.5–13.5% от суммы заказа) при трансграничной доставке в РФ. Экономику по марже нужно
понимать через ERP до полноценного запуска.

## GSC / SEO — статус

Проиндексированные страницы просели с ~88к до 28.9к (середина июня 2026, причина —
5xx ошибки при обходе краулером), частично восстановлено до 57.6к. План: фикс 5xx →
410 на мёртвых страницах → noindex на пустых карточках → sitemap ограничить ~50к
наполненными карточками → внутренняя перелинковка только на наполненные страницы.

## Стиль коммуникации с Романом (для справки агенту)

Roman — единственный разработчик и оператор бизнеса. В мобильном/веб-чате с Claude
предпочитает стратегическое обсуждение, а не построчную реализацию кода — для этого
используется in-editor агент. Ценит прямую аргументированную обратную связь и конкретику
над абстрактной теорией.
