# Global Parts — Контекст проекта для агента

Этот файл — справочник архитектурного и бизнес-контекста для in-editor агента.
Обновляйте его по мере крупных изменений в пайплайне.

## О проекте

Global Parts (shop.globalparts.kz) — интернет-магазин автозапчастей в Астане, Казахстан.
Модель: asset-light dropshipping от ~10 поставщиков (Rossko, Shatem, Interkom, ForumAvto,
TISS и др.) с доставкой день-в-день/на следующий день как ключевым конкурентным
преимуществом. Единственный разработчик и оператор — Roman.

Каналы продаж: Kaspi Marketplace (основной), собственный сайт, 2GIS, OLX, повторные/
реферальные заказы. Стек: Laravel/PHP/MySQL.

## Архитектура Kaspi-пайплайна

Основной поток команд:
```
prices:fetch → offers:aggregate → kaspi:match → kaspi:reprice →
kaspi:sync-feed → kaspi:feed-cleanup → kaspi:generate-xml
```
Еженедельно (поиск новых карточек): `kaspi:parse-sku` → `kaspi:bind-products`

### Ключевые таблицы
- `kaspi_initial_products` — неизменяемый источник истины, репрайсинг никогда его не трогает
- `supplier_offers` — слой агрегации, `UNIQUE KEY (sku, supplier_name, brand)`
- `kaspi_competitors` — конкурентные офферы по позициям
- `parts_catalog` — используется для подготовки Ozon-фида (скрейпинг публичных карточек Kaspi)
- `kaspi_feed_items` — колонка `bound` отмечает привязанные к мастер-карточкам товары

### Важные классы/команды
- `MatchKaspiSkuCommand.php` — матчинг по артикулу; здесь же константа `DISABLED_SUPPLIERS`
  для временного отключения поставщика без потери данных (сейчас используется для ForumAvto)
- `AggregateSupplierOffersCommand` — партиционирует офферы по `(sku, brand)`, не просто `sku`;
  здесь же `EXCLUDED_SKUS`, `BRAND_ALIASES` (напр. `lemfoerder`/`lmi` → `lemforder`),
  `QTY_OVERRIDE_KEYWORDS`, `QTY_OVERRIDE_ARTICLES`, `FIXED_COST_KEYWORDS`
- `RepriceKaspiCommand` — динамический репрайсинг; anomaly detection блокирует только
  понижение цены при `$flag === 'risk'`, повышения не блокирует
- `KaspiPriceCalculator` — `COMMISSION=0.125`, `TAX=0.04`, `FEES_DIVISOR=0.835`;
  прогрессивная маржинальная шкала (50к-120к сегмент — 35%, 120к+ — 34%),
  `MIN_ABS_MARGIN` — абсолютный пол в тенге, `min_margin_dumping` сегмент — намеренно
  ~15% каталога с минимальной маржой для конкурентного покрытия
- `GenerateKaspiXml` — здесь `EXCLUDED_NAME_PATTERNS`; XML namespace `xmlns="kaspiShopping"`,
  порядок элементов строго `model → brand → availabilities → price`
- `KaspiFeedCleanupCommand` / `deactivateStaleFeedItems()` — деактивация устаревших/
  осиротевших офферов
- `SlugHelper::brandToSlug()` — полная транслитерация кириллических брендов, обязателен
  `?string` type hint (NULL brand ломал слаги и давал 5xx)

### Матчинг: важный баг и фикс
Короткие артикулы (напр. `BW0010`) матчились по substring на карточки для `BW0010-07-2`,
что вызывало продажи ниже себестоимости. Исправлено: `normalizeArticle()` + word-boundary
regex вместо `str_contains()`, плюс fallback-цикл, постепенно упрощающий поисковый запрос
Kaspi при сохранении строгой фильтрации по артикулу.

## Поставщики — особенности парсеров

- **Kulan** (`kulanoil.kz`) — только колонка "Нур-Султан", `preorder_days=0`
- **ZakazAutoKostanay** — имя файла содержит `zakazauto` + `kostanay`/`kst`, `preorder_days=7`
- **Tstarter** — файл `Astana_ostatki_Tstarter`, 6 колонок, цены в KZT несмотря на
  заголовок "руб"
- **Interkom** — multi-sheet xlsx (`MultiSheetParserInterface`), `.xls` ~18MB падает
  тихо — вероятно memory/timeout при `SimpleXLS::parse()`
- **ForumAvto** — два парсера LP/GP; GP-поставщик удалён из БД полностью, LP реактивирован;
  сейчас LP временно отключён через `DISABLED_SUPPLIERS`
- **Phaeton/Shatem** — детекция приоритизирует `bodyLower` (тело письма) над `From`
  заголовком, т.к. письма часто пересылаются вручную
- **TISS** — API иногда возвращает пустой `offers` при реальном наличии на сайте
  (открытая проблема, см. ниже)

## Открытые технические задачи

1. **AdminPanelController — расхождение в графике**: `getDataByMonths()` /
   `groupOrdersWithStatsByPeriod()` за сентябрь 2025 показывает 10,550,437 вместо
   реальной суммы в БД 10,985,633. Следующий шаг: логировать `array_keys($stats)`,
   похоже на дублирующиеся ключи периода из-за локали в `translatedFormat`.

2. **TISS API пустые offers**: сайт TISS показывает реальный остаток, API — пустой
   массив. Следующий шаг: перетестировать на артикуле с подтверждённым наличием
   день-в-день, расширить лог `raw_body` до ~10000 символов, сравнить полный JSON
   с распарсенным количеством.

3. **504 на обычном поиске сайта — в процессе решения через прогрессивную
   подгрузку (начато 2026-08-15, не докручено, продолжать отсюда).**

   Исходная причина (лог `production.ERROR`, обнаружено 2026-08-15):
   `SparePartController::getSearchedPartAndCrosses()` (вызывается из
   `catalogSearch()` / роут `POST /getPart`) опрашивает 18+ поставщиков
   **строго последовательно** — `searchArmtek`, `searchGerat`,
   `searchShatem`, `searchPhaeton`, `searchTreid`, `searchTiss`,
   `searchKulan`, `searchFebest`, `searchForumAuto`, `searchIngvar`,
   `searchVoltage`, `searchBlueStar`, `searchInterkom`, `searchAdilPhaeton`,
   плюс условно `searchAutopiter`/`searchAvtozakup`/`searchRossko`. У
   каждого свой таймаут (2-8 сек через `curl`/`SoapClient`/`Http`,
   константы `CONNECTION_TIMEOUT=2`/`TIMEOUT=3`), но т.к. вызовы идут один
   за другим — суммарное время легко перескакивает 30-60 сек и обрывается
   по gateway timeout. Попутно найден и исправлен отдельный баг в той же
   функции (не причина 504): TypeError на `logSearchIfNotAdmin()` при
   отсутствии `partNumber` в запросе (лишний второй аргумент при
   однопараметрической сигнатуре + нестрогая типизация).

   Выбранное решение — не распараллеливание, а **прогрессивная загрузка**:
   рендерить страницу результатов мгновенно (без единого обращения к
   поставщику), а сами данные подгружать отдельными запросами по мере
   готовности, пока пользователь уже видит страницу. Решили так вместо

   `getShatemToken()` не использовался в `searchShatem()` вовсе, каждый
   вызов логинился заново; теперь `Cache::lock()` вокруг
   `cache()->remember('shatem_token', ...)` решает и это, но полная

### Чем отличается от Kaspi — важно
У Kaspi нет self-service загрузки фида: ссылку на XML нужно передавать персональному
менеджеру Halyk Market вручную, который сам настраивает импорт (~раз в час опрос) — это
подтверждено и официальным гайдом, и вики стороннего инструмента MarketRadar. **НО** у
Halyk Market есть отдельный полноценный REST API (`zagruzka-tovarov-po-api` в доках),
который куда ближе к Ozon, чем к статик-фиду Kaspi: реальный upload-эндпоинт с
возвращаемым ID и опросом статуса построчно (successCount/failCount/notMappedCount),
плюс отдельные эндпоинты на поиск/привязку к существующей карточке и на создание новой
карточки с нуля. Разбираться нужно именно в этом API, а не в ручной передаче ссылки
менеджеру.

### Авторизация
OAuth2 client credentials.
- `POST https://halykmarket.kz/gw/auth/token`
- Тело: `{"grant_type":"client_credentials","client_id":"HMM_<БИН>","client_secret":"..."}`
- `client_id` — выдаёт менеджер (формат `HMM_<БИН магазина>`), `client_secret` —
  приходит на почту при включении API.
- Ответ: `access_token` + `token_type=Bearer` + `expires_in=7199` (~2 часа) — токен
  нужно кэшировать и обновлять по истечении (тот же паттерн, что уже есть для
  Shatem-токена в `SparePartControllerTest::getShatemToken()` — `Cache::lock()` вокруг
  `cache()->remember()`, чтобы не долбить auth-эндпоинт на каждый вызов).
- Тестовый контур: `test2.halykmarket.com` / `test2-api.halykmarket.com` (для

### Поиск и привязка к существующей карточке (аналог kaspi:parse-sku → kaspi:match → kaspi:bind-products)
1. **Поиск**: `GET /gw/merchant/public/skus/search?q=<название или артикул>&page=&size=`
   → возвращает список кандидатов с `skuId` (главное поле, нужен на следующем шаге),
   `name`, `imageUrl`, `category{id,name,level}`, `marketUrl`.
2. **Привязка**: `PUT /gw/merchant/public/product/remaining/save-and-map-sku`
   Тело: `skuId`, `merchantProductCode` (наш артикул), `city.code`, `price`,
   `points.code` + `points.amount` (склад/остаток), `loanPeriod` (допустимо только
   3/6/12/24). Товар переходит в статус "На продаже".
   **Критично**: привязанный товар обязательно должен присутствовать в каждой
   последующей выгрузке фида, иначе автоматически уходит в архив — прямая аналогия с
   колонкой `bound` в `kaspi_feed_items`, тот же принцип нужно повторить в новой
   таблице под Halyk.

### Загрузка фида (аналог kaspi:generate-xml + отправка)
- **Загрузка**: `POST https://api.halykmarket.com/api/merchant/v1/offers/upload`
  (`multipart/form-data`, поле `file` — путь до XML) → `{"id": 11111}`.
- **Статус**: `GET /api/merchant/v1/offers/upload/status/{id}` →
  `status` (`CREATED`/`PROCESSING`/`COMPLETED`/`FAILED`/`SKIPPED` — последнее означает
  "идентичен предыдущей загрузке, не обработан повторно"), плюс `totalCount`/
  `successCount`/`notMappedCount`/`failCount`/`message`. `notMappedCount` — готовый
  сигнал, какие позиции нужно перепривязать через `save-and-map-sku`.

### Создание новой карточки (для того, что не найдётся поиском — самый трудоёмкий кусок)
Перед созданием доки явно требуют: "убедиться, что такого товара действительно нет в
каталоге" (сначала поиск, создание — только если не нашлось). Полный поток из 6 шагов:
1. `GET /gw/merchant/public/category/search?q=...` — поиск категории **3-го уровня**
   (обязательно самый глубокий уровень, не 1/2).
2. Поиск ID бренда (отдельный эндпоинт, аналогичный по форме категорийному).
3. `GET /gw/merchant/public/form/product/feature?categoryId=<id>` — форма характеристик
   под конкретную категорию: `classAttrAssignmentId`, `classAttrType`
   (`NUMBER`/`ENUM`/`STRING`/`BOOLEAN`), `required`, у `ENUM` — фиксированный список
   `classAttrValues` (значение выбирается, а не вводится свободным текстом).
4. Загрузка фото.
5. Отправка заполненной формы на модерацию.
6. Опрос статуса модерации.

**Почему это отдельная фаза работы, а не "просто ещё один шаг пайплайна"**: категории,
бренды и значения характеристик у Halyk — **своя таксономия**, не совпадающая с тем, что
есть в `parts_catalog` со скрейпинга карточек Kaspi. Нужен маппинг: наши
`category_top_code`/`category_group_code` → `categoryId` Halyk, наши бренды → `brandId`
Halyk, наши произвольные строки характеристик → конкретные `classAttrValueId` из ENUM.
Это разовая (и потом поддерживаемая) работа сопоставления справочников, качественно
сложнее, чем поиск+привязка к уже существующим карточкам.

### Архитектура пайплайна (по образцу Kaspi)
```
halyk:search-sku   → halyk:match → halyk:bind →
halyk:generate-xml → halyk:upload-feed → halyk:check-feed-status   [ещё не написаны]
                                              ↑
                              halyk:create-card (для notMappedCount / не найденных поиском)  [не написано]
```
Первая ветка (поиск → сопоставление → привязка) выбрана стартовой сознательно —
`halyk:create-card` вынесен в отдельную фазу (маппинг категорий/брендов/характеристик,
см. выше — качественно более трудоёмкая задача).

### Пилот на 100 позициях (реализовано И протестировано живьём 2026-08-21, результат — 10%, путь отставлен в пользу create-card)
- `database/migrations/2026_08_21_000001_create_halyk_sku_candidates_table.php` —
  `halyk_sku_candidates`: один `request_article` может иметь до 5 строк-кандидатов
  (топ выдачи поиска), `matched`/`bound` — булевы флаги состояния пайплайна.
- `app/Services/HalykMarketClient.php` — тонкий клиент: `token()` (OAuth2 client
  credentials, кэш на ~2 часа через `Cache::lock()`+`cache()->remember()`, тот же
  приём, что и `getShatemToken()` в `SparePartControllerTest`), `searchSku()`,
  `bindSku()`. Переключение прод/тест-контур — `HALYK_USE_TEST_ENV` в `.env`.
- `halyk:search-sku {--limit=100}` — источник артикулов: `kaspi_initial_products`
  (`sku`+`brand` там — реальный производственный артикул, не наш внутренний ID,
  проверено на случайной выборке: `101905611A`/vag, `PBK6905H`/patron и т.д., а не
  только внешне похожие на ID записи вроде `100001`/motodor). Строит запрос
  `"{brand} {sku}"`, шлёт в `GET /skus/search`, пишет топ-5 кандидатов на артикул.
- `halyk:match` — строгое сопоставление кандидата по артикулу: нормализация
  (`mb_strtoupper` + убрать дефисы) и regex с проверкой границы токена
  `(?<![A-Z0-9])артикул(?![A-Z0-9])`, портировано 1:1 из
  `ParseKaspiSkuCommand::filterByExactArticle()` — та же защита от бага BW0010
  (короткий артикул матчился по substring на карточки вида `BW0010-07-2`).
- `halyk:bind {--limit=100}` — `PUT save-and-map-sku` для сопоставленных;
  цена/остаток берутся из `kaspi_initial_products` (`price`/`stock`), `loanPeriod=3`
  (минимальный из допустимых 3/6/12/24, не обсуждали отдельно — безопасный дефолт).
  Явно падает с понятной ошибкой, если `HALYK_CITY_CODE`/`HALYK_POINT_CODE` не заданы
  — не привязывает молча в никуда.
- **Живой прогон 2026-08-21**: реальные креды получены от менеджера в тот же день,
  `HalykMarketClient::token()` — авторизация проходит. `halyk:search-sku --limit=100`
  и `halyk:match` прогнаны на реальных данных: **10 из 100 сопоставлено**. Вручную
  проверены и провалы, и успехи — матчер отработал строго и корректно (см. итоговую
  сводку в начале раздела "Halyk Market" за анализом ПОЧЕМУ так мало: либо поиск
  Halyk выдаёт нерелевантные результаты, либо только соседние артикулы того же
  бренда — товара с точным артикулом у них просто нет). `halyk:bind` осознанно НЕ
  запускался — 10 подтверждённых совпадений остались непривязанными, путь отставлен.
- Если направление всё же понадобится вернуть в работу: `halyk:search-sku --limit=N`
  → `halyk:match` → `halyk:bind` — все креды в `.env` уже настоящие, дополнительной
  подготовки не требуется.

### Простой статик-фид (реализовано И протестировано живьём 2026-08-21)
Пока с API-кредами тормозили, менеджер Halyk попросил прямо то же, что просят у Kaspi —
"ссылку, где лежит фид". Сделали по аналогии: `halyk:generate-xml` (по образцу
`kaspi:generate-xml`) генерирует `public/halyk_feed.xml` из `kaspi_initial_products`
(весь каталог целиком, ~95к позиций на 2026-08-21) по XSD-схеме `halyk_market`
(разобрана выше) — `XMLWriter`, порядок `model → brand → stocks → price → loanPeriod`.
Та же защита `EXCLUDED_NAME_PATTERNS`, что и в `kaspi:generate-xml` (проблемные
MEYLE-карточки по названию).

**Важный урок дня**: первая версия писала остаток атрибутом `stockLevel` на
`<offer>` — по XSD это формально валидно (`<stocks>` там `minOccurs="0"`), но Halyk
на практике НЕ считает товар доступным к покупке без полноценного
`<stocks><stock storeId=.../></stocks>`, привязанного к реальной точке продаж (сама
XSD-схема технически разрешает голый атрибут как альтернативу — их бэкенд, по факту,
требует другое). Обратная связь от менеджера была буквально "нет элемента stocks"
уже ПОСЛЕ того, как в файле формально появился валидный XML — сбивало с толку, пока
не проверили именно семантику приёмки, а не только XSD-валидность. Финальная версия:
`<stock storeId="Global_Parts_pp1" isPP="yes" available="yes" stockLevel="N"/>`
(`isPP="yes"` — наш единственный склад одновременно и пункт выдачи).
- `HALYK_MERCHANT_BIN`/`HALYK_STORE_ID` (или `HALYK_POINT_CODE`, тот же код) —
  теперь настоящие значения в `.env` (см. сводку в начале раздела). Без них команда
  пишет явные заглушки (`"УКАЖИТЕ_БИН"`/`"УКАЖИТЕ_STORE_ID"`) и предупреждает в
  консоли — Halyk такой фид не примет.
- Файл гитигнорится (`public/halyk_feed.xml` в `.gitignore`, та же причина, что и у
  `kaspi_feed.xml` — сгенерированный артефакт, история с git deploy уже поймала эту
  ошибку один раз, см. коммит "Stop tracking generated kaspi_feed.xml in git").
  Генерируется КОМАНДОЙ НА СЕРВЕРЕ (`php artisan halyk:generate-xml`), не пушится
  готовым файлом — агент может задеплоить код команды через git push, но сам файл
  на проде появляется только после ручного запуска команды (прямого доступа к
  серверу/SSH у агента нет, `kaspi:generate-xml` работает по тому же принципу и
  тоже не стоит на автоматическом расписании, см. `routes/console.php`).
- Как только файл появится на сервере — он живой по адресу
  `https://shop.globalparts.kz/halyk_feed.xml`, ссылку отправить менеджеру Halyk.
- Это НЕ то же самое, что `POST /offers/upload` из API-пилота выше — тот путь
  (реальный upload-эндпоинт с опросом статуса) всё ещё не реализован, статик-фид —
  временное решение, пока нет API-кредов.

### Пайплайн создания карточек (реализовано И проверено живьём 2026-08-22)
Команды: `app/Console/Commands/Halyk/HalykCreateCardCommand.php`
(`halyk:create-card {--limit=10} {--article=} {--dry-run}`) и
`HalykCheckCardStatusCommand.php` (`halyk:check-card-status`). Новая таблица
`halyk_created_cards` — по строке на попытку (`status`: `skipped`/`submitted`/
`moderation`/`reject`/`deleted`/`success`/`error`, плюс `skip_reason`/`comment`).

**Источник кандидатов**: `parts_catalog` ⋈ `supplier_offers` через уже существующий
`App\Services\SupplierOfferPricer` (тот же джойн `article_normalized`/
`brand_normalized`, что и в публичном каталоге сайта) — только реально в наличии
(`offer.stock > 0`), с фото, ещё не обработанные.

**Поток на каждую карточку**:
1. `searchSku` + строгая проверка по границе токена (портирована из `halyk:match`,
   защита от бага BW0010) — если уже есть на Halyk, пропуск
   (`already_exists_on_halyk`). На практике очень многие ходовые артикулы (свечи NGK
   и т.п.) уже там есть от автопереноса — реально до "создания" в тесте 2026-08-22
   доходила примерно 1 из 5-6 позиций.
2. Категория 3-го уровня. **Важный нюанс, не очевидный из документации**: наши
   колонки `category_top_title`/`category_group_title` — это только 2 верхних уровня
   из полного `characteristics.category_path` со скрейпинга Kaspi, а у Kaspi путь
   часто ГЛУБЖЕ (напр. "Свечи зажигания" — уже 3-й уровень у Kaspi, отдельно ни в
   одной колонке не хранится). Ищем по всем элементам `category_path` от самого
   глубокого к самому верхнему, пока не найдём совпадение 3-го уровня у Halyk.
3. Бренд — `searchBrand`, точное совпадение по имени в приоритете.
4. Форма характеристик (`getCharacteristicsForm`) + попытка заполнить ОБЯЗАТЕЛЬНЫЕ
   атрибуты значениями из `parts_catalog.characteristics` (структура та же, что и в
   `partInfo` — `specifications[].features[].featureValues[].value`). Если
   обязательный атрибут не удаётся найти — карточка целиком пропускается
   (`missing_required_attr:...`), не отправляем с дырами в обязательных полях.
5. Фото — Halyk принимает ТОЛЬКО файлы (multipart), не ссылки: скачиваем реальные
   файлы с Kaspi CDN и грузим их. Заявленные в их доке требования (белый фон,
   строго квадрат 500-2000px, минимум 3 шт) **на практике не проверяются самим
   upload-эндпоинтом** — проверено вживую: приняли фото 403×500 (не квадрат, ниже
   минимума по ширине) с HTTP 200 без единой жалобы. Похоже, это soft-guidance для
   модерации, а не hard-валидация при загрузке — так что грузим что реально есть
   (обычно 1 фото на карточку), а не блокируемся на препроцессинге картинок заранее.
6. Отправка на модерацию (`submitForModeration`) → успех даёт
   `{"productDraftStatus":"CHECK","id":<int>}`.

**Два реальных бага, найденных живым тестированием (не вычислить по одной
документации)**:
- `GET /category/search` возвращает **массив ПУТЕЙ** (breadcrumb от 1-го уровня до
  найденного узла), а не плоский список категорий — первая версия кода ожидала
  плоский список и падала с "Undefined array key". Поправлено — разворачиваем все
  пути, ищем узел `level===3` среди всех.
- `POST /draft/product/moderation` отвечает **`HTTP 202 Accepted`** на успех, а не
  200 — `Illuminate\Http\Client\Response::ok()` в Laravel проверяет строго `=== 200`,
  из-за чего реально успешная отправка (карточка ушла в очередь, `id` есть в ответе)
  ошибочно репортилась как провал. Заменили на `->successful()` (весь диапазон 2xx)
  во ВСЕХ методах `HalykMarketClient` на всякий случай, не только в этом одном —
  остальные (`bindSku` особенно, PUT-запрос) живьём ещё не проверялись, могли бы
  преподнести тот же сюрприз.

**Статус первого живого теста**: артикул `349067` (KYB, амортизатор задний) — фото
загружено, категория/бренд найдены, отправлено на модерацию, подтверждён статус
`MODERATION` в очереди через `halyk:check-card-status`. Результат модерации (SUCCESS/
REJECT/DELETED) на конец дня 2026-08-22 ещё не известен — это первый реальный сигнал
о качестве пайплайна, особенно по двум известным слабым местам ниже.

**Известные осознанные пробелы (не скрыты, задокументированы в коде)**:
- **Вес/габариты — 0% покрытия** во всём `parts_catalog` (проверено на всех 56647
  публичных карточках) — но `weight`/`width`/`height`/`depth` есть в форме
  submission и выглядят как обязательные (присутствуют в примере из документации).
  Сейчас — грубые дефолты-заглушки (`DEFAULT_WEIGHT_KG=0.5`, `WIDTH/HEIGHT/DEPTH_CM=15`
  в `HalykCreateCardCommand`) под "среднее мелкое автозапчастье". Если модерация
  начнёт заворачивать карточки конкретно из-за этого — придётся либо считать по
  категориям, либо вводить руками.
- **attrs-маппинг — простое совпадение по имени/значению**, не строгая таксономия.
  На реальном тесте (349067) в attrs проскочило подозрительное значение "Левая"
  (сторона) для амортизатора, где это не факт что релевантно, и один и тот же бренд/
  модель ("Volkswagen"/"Tiguan") дважды под разными `id` (вероятно, форма Halyk
  содержит два похожих по смыслу атрибута в разных блоках) — не обязательно ошибка,
  но стоит свериться с реальным результатом модерации, прежде чем масштабировать на
  много карточек разом.

## GSC / SEO — статус

Проиндексированные страницы просели с ~88к до 28.9к (середина июня 2026, причина —
5xx ошибки при обходе краулером), частично восстановлено до 57.6к. План: фикс 5xx →
410 на мёртвых страницах → noindex на пустых карточках → sitemap ограничить ~50к
наполненными карточками → внутренняя перелинковка только на наполненные страницы.
